## 几个名称分别是什么

| 名称 | 可以怎样理解 | 为什么需要 |
| --- | --- | --- |
| 工作区 | 你正在编辑的文件 | 修改尚未自动进入历史 |
| 暂存区（add） | 下一次存档的文件改动清单 | 挑出本次完成的内容，避免混入草案或凭据 |
| 提交（commit） | 本机的一份有说明、可追溯的版本记录 | 出问题时能查出修改原因，并制作撤销提交 |
| 分支（branch） | 给一条开发路线起的名字，指向一个提交 | 新功能可以独立开发，主线保持清楚 |
| main | 本项目已整合开发成果的主线 | 作为下次开发的共同起点；目前仍未正式发布 |
| origin | 本仓库 GitHub 地址的本地简称 | 命令不用反复写完整地址 |
| origin/main | 最近一次获取到的 GitHub main 位置 | 只是本机记录，fetch 后才反映远端新变化 |
| 获取（fetch） | 更新远端位置记录 | 先了解 GitHub 的变化，不直接改当前编辑文件 |
| 合并（merge） | 把另一条路线的提交接入当前分支 | 汇总已经完成的工作，保留来源和历史 |
| 推送（push） | 把本机提交及分支位置送到 GitHub | 远端保存和协作；未提交文件不会被顺带上传 |

本项目的日常顺序是：判断分支 → 编辑 → 验证 → 选择改动暂存 → 本地提交 → 提请确认推送/合并范围 → 按批准范围执行。一个阶段可以有多次小型、完整的提交，不必一直等到整个项目完成；权限与工程约束以 [AGENTS.md](../../AGENTS.md) 为准。

## 这次具体做了什么

原来开发分支已有新版界面、账号管理和 U4 等成果，main 较旧；同时 GitHub main 独有一笔语言统计修正。两条路线各有自己的提交，因此需要保留双方历史再合并，不能把其中一边直接覆盖掉。

当前工作区还留有待批准草案和其他本机改动。为保持这些文件原样，这次在独立 worktree（同一仓库的另一个工作目录）中合并。先整合本地/远端 main，再把完成的开发分支合入 main；文档冲突按新旧事实核对，业务文件保持 U4 基线。

合并完成后，以普通、非强制推送更新 GitHub main 与开发分支；这次两条分支一起使用 `--atomic`，服务器接受时两者一起更新，拒绝时两者都不更新。最后用远端查询核对编号，再将日常工作区切到 main。原开发分支及方案一备份保留，没有删除原提交。

合并提交记录两条历史的接合点，便于追溯本次整合。冲突表示 Git 无法替人决定同一处文本应保留什么，需阅读双方内容后解决，并不等于文件丢失。

## 以后怎样开发

先在仓库根目录执行 `git status --short --branch`，看当前分支及未提交内容。有待保留的修改时先核对归属，不强行切换或丢弃；当前草案和两份文档修改就是这样的待处理内容。

工作区适合切换、且任务适合从主线独立开始时，以下命令获取远端主线并直接建立功能分支，不先改动本地 main：

```powershell
git fetch origin
git switch --no-track -c codex/example-task origin/main
```

确认 fetch 成功后再执行下一步，示例分支名要换成本次任务的名称。`--no-track` 避免误把功能分支的上游设为 origin/main，首次推送目标在确认时明确。相关工作可以复用现有功能分支；有依赖时先说明基线，不能机械地一律从 main 开始。开分支本身不代表需求已获批准。

完成一个独立闭环后，先实际验证，再执行 `git diff` 审查；只对确认归属的具体路径执行 `git add -- 文件路径`。用 `git diff --cached` 检查将提交的内容，之后 `git commit -m "说明改动目的"`。本地提交由助手主动完成；收口时主动说明拟推送/合并的目标分支、提交范围及验证结果，等待用户确认 GitHub 写操作和合入 main。

达到本阶段批准范围的验收标准后即可评估收口，不必等待整个大计划结束。用户确认的范围决定执行哪些推送/合并；完成开发不自动取得远端授权。旧开发分支可保留作历史参考，已经合并后不继续承载新任务。

## Git 能保存到什么范围

GitHub 同步代码不等于部署网站，也不会自动替数据库执行迁移。本次没有上线、创建正式标签或 Release。

被忽略的密码、运行密钥、数据库、Redis、头像实体文件、依赖和本机备份不会自动进入 GitHub。因此“代码已推送”不等于“全部运行数据已有备份”；旧代码也不保证能直接连接新数据库运行。

误合并或功能需要撤销时，先定位提交和影响，再考虑新增 `git revert` 撤销记录；合并提交还需明确保留哪条主线，不能机械套用命令。不使用强推、`reset --hard` 或 `clean -fd` 来整理当前工作区。
