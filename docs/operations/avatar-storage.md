# 本地头像存储与迁移

状态：2026-10-30，P4 已改为私有待审后发布；昵称/头像审核、配额、接口与迁移详见[资料审核说明](profile-moderation.md)。尚未接入 OSS。

## 使用和位置

个人中心点击头像 → 选择 JPEG/PNG → 拖动、方向键移动或按钮缩放 → 提交审核，OWNER 明确通过后公开。原图不超过 5 MB、4096×4096，先在浏览器读取尺寸再解码；取消不上传。最终上传单张 256×256 图片，服务端独立检查真实格式、尺寸与 256 KB 体积上限，重新编码为 JPEG，透明区域铺白，不保留原文件、EXIF 或用户文件名。

本机 `PolyhouseApplication` 的 Git 忽略个人配置已设置 `POLYHOUSE_AVATAR_DIRECTORY=E:\polyhouse-data\avatars`。该目录独立于源码、Git 和构建输出；图片不存入 MySQL 或 Redis。数据库已有的 `sys_user.avatar` 只存 `/api/media/avatars/<随机版本>.jpg`，P4 需追加 008 迁移，并将申请状态、审核版本及私有键放在独立表，MySQL 不存图片字节。实际大小随图像内容变化，不能承诺固定 KB 数。

`Initialize-LocalAuth.ps1` 在没有已有设置时，选择项目所在磁盘的 `polyhouse-data\avatars`；可通过 `-AvatarDirectory` 指定绝对路径，重复执行保留原值及既有密钥。`Invoke-LocalAuth.ps1 -Action Run` 复用同一预设。其他机器或部署环境必须设置持久目录；未配置时上传返回 503，不静默使用系统临时目录。

multipart 限制为文件 256 KB、整包 272 KB，内存阈值 272 KB，服务端 ImageIO 也使用内存流，避免头像上传临时文件持续占用 C 盘。该限制当前应用于所有 multipart 请求，日后新增其他上传业务需单独设计配额；当前妙替/妙压仍按策划书在端侧处理文件。

## 接口与规则

- `POST /api/auth/avatar/submissions`：Bearer 完整登录，multipart 字段 file/requestId，返回 `Result<ProfileSubmissionVO>` 的申请编号、状态及额度；不返回新公开头像。旧 `POST /api/auth/avatar` 已关闭返回 409；新页面对旧后端的新地址得到 404，避免混用版本时旧后端先公开图片。
- `GET /api/media/avatars/<32位小写十六进制>.jpg`：公开的只读图片资源入口，返回 JPEG 图片字节。只有此名称格式可读取，清理标记、目录列表、任意文件与符号链接不开放；这是静态资源，不是返回 Entity 的业务 Controller。访问地址不含用户编号或磁盘路径；公开头像链接不是隐私访问控制。
- 每个上海自然日最多成功提交 5 次头像申请，昵称 2 次。次数按独立申请表的成功入库记录统计，驳回/替代也计次；同 requestId/同内容不重复计次，失败/回滚不计次。升级当天叠加旧 ext_json.avatarUpload 的已用次数，不改其他配置。网络结果未知先刷新申请状态，重试原内容沿用相同编号，不自动发送写请求。
- 非法图片 400、未认证 401、上传超限 413、当日次数用完 429、存储未配置或不可写 503。超限由统一异常处理返回 JSON。

导航、个人小窗和个人中心共享头像组件；只加载本项目受控地址，不请求旧第三方默认头像。加载失败或未上传时显示昵称首字。随机版本名配合一天缓存，换图后使用新地址；多标签页收到资料缓存变化后重新请求服务端，不信任缓存中的角色或头像。上传和资料恢复有版本检查，旧响应不能覆盖后来登录的身份；提交本身不更新公共资料，批准后刷新 /me 获取新头像。

头像编辑额外核对本次编辑编号、会话及弹窗状态：关闭、换号或离开页面时释放图片并作废旧编码/上传回调，旧成功和旧失败均不能关闭新弹窗、写入新错误或解除新上传的忙碌状态。当前操作明确失败时保留裁剪图供重试；网络或 5xx 异常显示结果未确认，建议先核对申请状态。前端作废回调不能撤销已送达服务器的请求，也不代表服务器回滚。

## 文件与数据库一致性

先保存到公开目录的同级私有目录 `E:\polyhouse-data\avatars-pending`，申请与最小审计提交后等待审核。本人/OWNER 通过带 Bearer 的图片接口预览，响应 no-store；没有匿名静态映射。私有资源拒绝符号链接与路径穿越，单图 256KiB、单实例最多 512 个图键；待审七天，替代/驳回/过期/账号失效后限量清理。

通过才保存新的公开 JPEG 地址并定向更新头像，提交成功后清理旧图/私有图；明确回滚清理新文件并保留旧资料/旧待审。数据库与文件不是一个原子事务，UNKNOWN 时不误删可能已提交的新图。删除失败持久标记并重试；超过 24 小时的私有孤儿须核对数据库无引用才回收，公开孤儿仍需备份后人工核对，不能只按文件年龄批量删图。

软注销沿用原资料保留语义；失效账号待审不再发布并会清理，但不等同于永久擦除其公开历史图片。OWNER 可显式审核/下架资料，头像恢复默认；旧客户端缓存/已下载副本不能保证即时消失。永久擦除、OSS 和多实例共享配额未实现。备份与兼容回退按[资料审核说明](profile-moderation.md)执行，不能直接切回允许立即上传发布的旧后端。

## 上线前接 OSS

当前下载由 Spring 静态资源处理，已提供 `Cache-Control: max-age=86400, public`；图片读取不调用用户查询或图片解码。后续单机部署可以改由 Nginx 直接读取同一受限图片目录，保留既有 URL 和缓存规则，并拒绝隐藏清理目录/目录列表。这样可减少应用处理图片下载的负担，但不能代替备份、磁盘容量规划或多实例共享存储；本轮仅讨论，未配置 Nginx。参考 [Nginx 静态文件与 sendfile](https://docs.nginx.com/nginx/admin-guide/web-server/serving-static-content/)。

数据库 BLOB 会增加数据传输及存储资源需求，但是否影响缓存命中率取决于访问模式和资源预算；不能把它等同于 HTTP 缓存失效或应用内存固定翻倍。HTTP 缓存由响应头等协议语义决定，与图片最终取自磁盘还是数据库没有必然绑定。当前方案没有向 MySQL/Redis 写图片本体。参考 [MySQL BLOB 优化](https://dev.mysql.com/doc/refman/8.0/en/optimize-blob.html)、[HTTP 缓存说明](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching)。

`AvatarStorage` 隔离保存/删除操作，当前实现为 `LocalAvatarStorage`。以后新增 OSS 实现，并明确访问域名、最小写入权限和费用提醒；长期 AccessKey 不进入浏览器。

迁移还要复制现有文件、检查完整性、兼容旧访问地址或更新资料，并安排数据库和图片一致的备份。不能只改一个配置就断言迁移完成；容器部署必须挂载持久卷，多个后端实例不能各自保存到互不共享的磁盘。候选方案和当时的价格资料见[方案比较](../design/avatar-upload-options.md)。
