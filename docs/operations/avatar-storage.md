# 本地头像存储与迁移

状态：2026-10-27，本地上传已实现；尚未接入 OSS。

## 使用和位置

个人中心点击头像 → 选择 JPEG/PNG → 拖动、方向键移动或按钮缩放 → 保存。原图不超过 5 MB、4096×4096，先在浏览器读取尺寸再解码；取消不上传。最终上传单张 256×256 图片，服务端独立检查真实格式、尺寸与 256 KB 体积上限，重新编码为 JPEG，透明区域铺白，不保留原文件、EXIF 或用户文件名。

本机 `PolyhouseApplication` 的 Git 忽略个人配置已设置 `POLYHOUSE_AVATAR_DIRECTORY=E:\polyhouse-data\avatars`。该目录独立于源码、Git 和构建输出；图片不存入 MySQL 或 Redis。数据库已有的 `sys_user.avatar` 只存 `/api/media/avatars/<随机版本>.jpg`，无需数据库迁移。实际大小随图像内容变化，不能承诺固定 KB 数。

`Initialize-LocalAuth.ps1` 在没有已有设置时，选择项目所在磁盘的 `polyhouse-data\avatars`；可通过 `-AvatarDirectory` 指定绝对路径，重复执行保留原值及既有密钥。`Invoke-LocalAuth.ps1 -Action Run` 复用同一预设。其他机器或部署环境必须设置持久目录；未配置时上传返回 503，不静默使用系统临时目录。

multipart 限制为文件 256 KB、整包 272 KB，内存阈值 272 KB，服务端 ImageIO 也使用内存流，避免头像上传临时文件持续占用 C 盘。该限制当前应用于所有 multipart 请求，日后新增其他上传业务需单独设计配额；当前妙替/妙压仍按策划书在端侧处理文件。

## 接口与规则

- `POST /api/auth/avatar`：Bearer 登录，`multipart/form-data` 字段 `file`；DTO 校验，统一 `Result<AvatarVO>`，成功 `data={avatar, remainingToday}`。用户编号只来自会话，不从表单取值。按用户已明确要求，普通 USER 也可使用此基本资料能力；只处理受限小图，不开放高开销工具或收费接口，后者仍遵守 INSIDER 闸门。
- `GET /api/media/avatars/<32位小写十六进制>.jpg`：公开的只读图片资源入口，返回 JPEG 图片字节。只有此名称格式可读取，清理标记、目录列表、任意文件与符号链接不开放；这是静态资源，不是返回 Entity 的业务 Controller。访问地址不含用户编号或磁盘路径；公开头像链接不是隐私访问控制。
- 每个上海自然日最多成功修改 5 次；次数存于该用户 `ext_json.avatarUpload`，与头像在同一行锁和事务内更新，保留其他扩展设置。失败、取消不扣次数；并发请求也不能绕过上限。
- 非法图片 400、未认证 401、上传超限 413、当日次数用完 429、存储未配置或不可写 503。超限由统一异常处理返回 JSON。

导航、个人小窗和个人中心共享头像组件；只加载本项目受控地址，不请求旧第三方默认头像。加载失败或未上传时显示昵称首字。随机版本名配合一天缓存，换图后使用新地址；多标签页收到资料缓存变化后重新请求服务端，不信任缓存中的角色或头像。上传和资料恢复有版本检查，旧响应不能覆盖后来登录的身份或新头像。

## 文件与数据库一致性

先写新图片，再提交头像和次数；成功提交后删除旧图，明确回滚后删除新图，保留旧图。删除失败写入目录下的 `.cleanup` 标记，每分钟最多重试 32 项，进程重启后仍可重试；此目录不对网页公开。

本地文件和 MySQL 并非一个原子事务。强制结束进程、磁盘损坏或事务结果未知时，可能留下不再被引用的图片；结果未知时保留新旧文件，避免误删可能已提交的新图。尚未实现按数据库引用定期核对全部孤立图；上线前应补审计与备份恢复，不直接按文件年龄批量删除。清理标记本身也写入失败时只记录安全警告，需排查磁盘权限/空间。

软注销仍沿用现有资料保留语义，不把它当成永久删除用户图片。永久擦除、头像审核、重置默认头像和管理员管理入口尚未实现。

## 上线前接 OSS

当前下载由 Spring 静态资源处理，已提供 `Cache-Control: max-age=86400, public`；图片读取不调用用户查询或图片解码。后续单机部署可以改由 Nginx 直接读取同一受限图片目录，保留既有 URL 和缓存规则，并拒绝隐藏清理目录/目录列表。这样可减少应用处理图片下载的负担，但不能代替备份、磁盘容量规划或多实例共享存储；本轮仅讨论，未配置 Nginx。参考 [Nginx 静态文件与 sendfile](https://docs.nginx.com/nginx/admin-guide/web-server/serving-static-content/)。

数据库 BLOB 会增加数据传输及存储资源需求，但是否影响缓存命中率取决于访问模式和资源预算；不能把它等同于 HTTP 缓存失效或应用内存固定翻倍。HTTP 缓存由响应头等协议语义决定，与图片最终取自磁盘还是数据库没有必然绑定。当前方案没有向 MySQL/Redis 写图片本体。参考 [MySQL BLOB 优化](https://dev.mysql.com/doc/refman/8.0/en/optimize-blob.html)、[HTTP 缓存说明](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching)。

`AvatarStorage` 隔离保存/删除操作，当前实现为 `LocalAvatarStorage`。以后新增 OSS 实现，并明确访问域名、最小写入权限和费用提醒；长期 AccessKey 不进入浏览器。

迁移还要复制现有文件、检查完整性、兼容旧访问地址或更新资料，并安排数据库和图片一致的备份。不能只改一个配置就断言迁移完成；容器部署必须挂载持久卷，多个后端实例不能各自保存到互不共享的磁盘。候选方案和当时的价格资料见[方案比较](../design/avatar-upload-options.md)。
