## 2. Git 方案与渐进迁移（Q0）

这是一套适合单人/少量协作者的双主线流程，不套用完整 Gitflow 的所有分支。关键是变更可追溯、任务隔离、验收后晋级和可撤销，不靠分支数量证明“企业级”。长期约束归根 [AGENTS.md](../../AGENTS.md)，此处说明本阶段的落地方式。

| 分支 | 从哪里来、到哪里去 | 用途 |
| --- | --- | --- |
| `main` | 接收验收完成的 dev 或必要的紧急修复 | 稳定、可交付基线；实际已部署版本另以获批发布记录/提交标识，main 不自动等于线上版本 |
| `dev` | 首次从已核对的 main 建立，接收任务分支 | 下一批工作的集成线，应可构建/普通测试通过；允许尚未发布，不接收占位半成品 |
| `codex/feat-<任务>`、`codex/fix-<任务>`、`codex/docs-<任务>`、`codex/chore-<任务>` | 通常从 dev 建立、回到 dev | 新功能、修复、文档与维护，各自限定任务；名称短、职责清楚，不每个提交另建分支 |
| `codex/hotfix-<任务>` | 从实际需要修复的 main 基线建立；合回 main 后同步 dev | 线上/稳定线急修；若 main 已含尚未部署变更，先核对线上 SHA，不把整批未发功能一起上线 |
| `codex/release-<候选>`（条件使用） | 仅当确有“冻结本批、dev 同时开发下一批”需求时从 dev 建立 | 当前先冻结 dev 验收即可，不预建常驻 release/test/staging 分支；使用时修复须同步回 dev |

### 2.1 先迁移工作方法，再配置远端

1. 核对本计划提交与 main 的关系；规划若尚未合主线，先保留/整合规划提交，不能只从旧 main 开 dev 而丢失入口。核对本地/远端引用和工作树归属，保护已有报告、未跟踪/忽略文件、私有运行配置。
2. 明确唯一 dev 起点并建立本地 dev，任务在独立 `codex/` 分支进行；main 保留本轮已收口基线。在远端 dev 未建立前，可在已核对的本地 dev 上开展本地工作；首次推送时再确认目标及范围。
3. 后续通常是任务分支 → PR（合并请求）→ dev → 候选验收 → PR → main。主线合并默认保留提交和合并来源，不使用变基改写已共享历史；目标已包含完整验收历史时可快进。合并后新增冲突解决/代码修改必须重新验证受影响项，不能只看“无冲突”。
4. PR 写清问题/结果、范围、验证与未验项、兼容/回退；任务提交保持完整闭环，中文为主。单人阶段做自审与二次复核，用户确认晋级；不能把 AI 自审冒充另一位 GitHub 审核人。将来有真实第二位维护者再要求其审批。
5. main 的紧急修复及时合回 dev；从 dev 晋级 main 后同样核对两线祖先/差异，避免下一轮遗漏修复。多代理/工具并行时每个任务独立工作树，不能因目录不同就假定共享文件无冲突。
6. 旧分支按已合并、仍有独有提交、备份、工作树占用分类。未确认未提交/未跟踪/忽略资料及恢复需求前不删除；本轮已要求保留的两个原目录继续保留。移除分支指针不等于合并目录，移除工作树也不是代码合并步骤。

### 2.2 远端门禁与 CI（先设计，落地须确认）

- 拟保护 main、dev：经 PR、必要检查成功、讨论已解决，限制删除/强推，管理员同样遵守。不同时要求线性历史却采用 merge commit；不启用自动部署，也不设置自动合入绕过用户确认。
- 先核对仓库可见性、账号套餐、可用权限和真实维护者人数；暂未读取/核实当前远端保护配置，不声称已有门禁。缺少可用功能时记录限制，以相同检查/审核流程过渡，不虚构保护已生效。
- CI（持续集成，即每次 PR 自动检查）先覆盖无真实私密凭据的普通编译/单测/静态/构建、技能完整性；沿用现有依赖锁和 JDK 21，不为 CI 升级项目版本。按现有脚本支持选择运行环境，最小只读权限，不用项目正式密钥，不把高权限运行器暴露给不可信 PR。
- 使用稳定、唯一的检查名称，检查确已成功运行后再设置 required；文档变更不能因路径过滤让必需检查永久等待。真实 MySQL/Redis 专项、浏览器、备份恢复单列，普通 CI 跳过实例测试必须显式汇报。
- 分支、环境与部署解耦：dev 不是一台服务器，合入 main 也不自动执行数据库迁移或发布。首次 dev 推送、PR、保护规则和 CI 发布前提交具体变更供确认。

参考：[GitHub flow](https://docs.github.com/en/get-started/using-github/github-flow) 的短期分支/PR/反馈流程、[GitHub 分支保护](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches) 的检查与审批能力。`main + dev` 是结合本项目及用户偏好的选择，不宣称是 GitHub flow 的原样定义或唯一企业标准。

Q0 验收：能说明当前每条活动线的基线/归属/目标，任务有唯一分支和工作树；历史目录未丢失；明确哪些本地完成、哪些远端待授权。CI 配置可与 Q1～Q3 并行准备，不能用搭平台拖延已明确的界面修复。

## 3. Q1：工具页面骨架与视觉尺度统一（第一实施闭环）

优先对象：妙替与妙压；核对相邻导航/页脚与共享组件。随后扩展到登录/个人页/管理工作台，按信息类型统一尺度，不强迫营销首页、表格与工具表单采用相同列数或高度。

1. 留同条件桌面/手机截图和尺寸表：页面最大宽度、边距、介绍区、卡片内边距、栏距/比例、标题层级、字体行高、圆角/边线、空态最小高度、按钮/表单高度、断点。
2. 以现有妙替 1320px 工具容器为首个对照候选，核对妙压在该宽度下的可读性与预览；不直接把 1320 强加给全站。统一工具页对齐线、介绍区/主卡片尺度，消除无意差异；业务内容增长导致的高度差允许保留，不靠固定高度裁掉表单或强造等高。
3. 先给出目标尺度/关键对照供核对；重大比例/布局取舍给用户选项后再做。样式优先局部收敛；确认两页确实共用后才抽取稳定的小型共享外壳/变量，不重构整个目录或重写 Element Plus。
4. 每次只改可验证区域，核对目标、相邻区域与复用处；保留首页粉色光晕、工具封面的特色，不换整体配色/品牌，不重排无关个人工作台。

Q1 验收：同一视口两工具外层对齐、尺度有明确依据；手机单栏、桌面双栏与实际断点前后无遮挡/横溢出/入口丢失；长文件名、长提示、空态/成功/失败状态仍可用。至少检查 320/390/768/1024/1440 及改动断点 ±1（缩放须记录实际 CSS 宽度），鼠标和 Tab 都实际操作。前端构建/静态检查与必要测试实际通过，不仅比较截图。

## 4. Q2：交互与前端故障状态收敛

- 业务按钮/文件入口的悬停、按下、禁用、Tab；输入/选择框连续单层焦点，弹窗焦点进入/返回、Esc/背景点击语义、触屏点击区域与放大后可用性。
- 统一空态、处理中、可取消、部分失败、全部失败、重试、下载/放弃；避免过期下载地址、旧任务回调复活、重复提交或失败后丢失用户输入。
- 妙替：选择文件/目录、500 候选与实际处理限额、跳过/选回、编码异常、统计/定位边界、JSON 全量恢复、草稿与分享冲突、多标签页存储冲突/禁用。定位标记不得进入下载正文。
- 妙压：单/批量、目标范围、取消与重试、DPI/COM、实际输出 MIME/后缀、透明合成、部分失败 ZIP；容量单位明确。解析 KB/MB 的既有兼容行为先核对，不能只改字面而改变用户旧输入含义。
- 会话与管理页：登录恢复/退出、换号后旧响应、首次改密、网络错误与权限错误、重复操作和未知结果核对；不因 UI 整理弱化角色/动作/目标校验。

Q2 验收：每个确认问题有复现、最小修复、适用自动测试与真实交互证据；每个修复独立提交，未复现线索不标完成。保持本机不上传、原文件不覆盖、草稿默认关闭等既有产品边界。

## 5. Q3：后端深度复核与真实隔离验证

围绕真实入口与状态流，不只搜索 TODO 或堆测试数量。先逐项核对现有覆盖，再补缺口；没有证据不批量改写稳定代码。

| 链路 | 重点检查 | 证据 |
| --- | --- | --- |
| 认证/权限 | 未登录/过期/伪造 Token，USER/ADMIN/INSIDER/OWNER 精确授权，DTO/VO，公共注册关闭、首次改密限制 | Controller/Service 测试 + 角色/目标矩阵 + 真实隔离 HTTP |
| 会话/并发 | 改密/封禁/解封/重置三端撤销，旧会话恢复不能复活，换号迟到，重复/并发写入与版本冲突 | 原子性、审计、幂等、数据库事实核对 |
| 开户/管理 | 唯一 OWNER、禁止管理 OWNER、一次凭据、未知结果只查询不盲重放；最小数据披露 | 隔离临时账号与异常响应/并发场景 |
| 资料/媒体 | 先审后发、私有图鉴权、失效/过期待审、路径穿越/链接/超限、公开/私有目录和媒体响应头 | 真文件解码与权限、数据库/文件引用对应 |
| 事务/依赖故障 | MySQL/Redis/文件操作失败、事务回滚/提交未知、清理重试、请求上下文释放 | 故障前后事实，不能只看返回码 |

- 普通检查复用 `polyhouse/scripts/Test-Project.ps1`；真实专项按运维文档分别执行 `Invoke-LocalAuth.ps1 -Action Verify` 的 `-AccountSecurityOnly`、`-AccountProvisioningOnly`、`-AccountManagementOnly`、`-ProfileModerationOnly`，不组合互斥开关。
- 先 Inspect 私有预设，仅用随机隔离库、专用 Redis 键、临时媒体目录；不在开发库运行含 OWNER 夹具的全量实例测试，不输出或重新索取已有密钥。新增隔离验收代码须保留失败后精确清理与清理断言。
- 跨端行为检查前端请求、服务端决策及持久化事实；数据库/Redis 不可用与 HTTP 响应中断分别测。新凭据的真实 UI 输入按工具交接规则执行，不把自动 HTTP 验证说成用户已在浏览器完成。

Q3 验收：高风险矩阵有本阶段可追溯证据，真实专项不被普通测试的 skip 混淆；任何越权、真实数据损害、会话复活、不可恢复丢失均阻断候选。依赖不可用则记录未验及下一动作，不用历史成功代替。

## 6. Q4：组合回归、可靠性与候选冻结

- 普通前后端检查、技能检查及其安全测试，记录真实执行数/跳过原因；CI 按 2.2 方案经批准后落地。仅文档闭环不为凑验收重复全量构建。
- 组合路径：匿名两工具 → 登录/个人资料 → 账号管理/审核 → 换号/退出 → 返回工具；重点看共享组件、导航/弹窗、状态残留及资源释放，不重置真实用户数据。
- 从当前限额构造小/典型/边界/超限与损坏样本；测连续运行/取消/离页的 Worker、对象 URL、内存趋势、主线程卡顿和下载，结果按真实设备/浏览器说明。后端 P95/P99/并发只在明确本机隔离预算下测试，不给“企业级高性能”空结论，不对真实服务压测。
- 主验证覆盖可用的 Chromium/Edge；Firefox/Safari、移动端真实设备与 AVIF 根据环境补验，未具备条件就声明具体支持边界/兼容降级并让用户知情，不伪造跨浏览器通过。
- 冻结候选提交 SHA：记录配置/依赖锁、迁移清单和实际构建产物来源。验收后候选改变就按影响重新检查，不能拿不同源码的报告发版；不得混入下一批未验功能。

Q4 验收：无阻断/高影响未解决问题；已知低影响问题逐项写影响、规避和是否接受，不能用任意固定分数掩盖风险。形成“已验、未验、阻塞、明确范围外”清单及可重复入口。
