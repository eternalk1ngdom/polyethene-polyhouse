## 三、内容和可用性如何落地

### 1. 项目说明与当期观察分别生成

项目说明回答用途、场景、机制、差异、适用边界，绑定仓库身份、资料版本、模型、规则和生成时间。首选兼容现有页面的方案：`definition` 写用途，`painPoint` 用连贯段落写场景和变化，`highlights` 写机制及作用，`comparison` 只放有依据的比较，限制与推断沿用独立字段。先用现有输出上限验证信息量；在术语后解释一次，把空间留给真正有区别的设计，避免逐栏重复一句话。

对于“解决什么问题”，把首屏的一句话当中心句，紧接的正文用一个场景写出原先的难处、项目介入的步骤和最后可用的结果。材料充分时参考 140～220 字，正文沿用既有 250 字校验上限，材料薄时允许短写。先保留同一次请求共享证据和预算。读者试读若仍有明确缺口，再评估选段、篇幅和拆请求各能解决哪一个问题。第 4 步同时核对发布完成后的新生成、复用及未通过校验等计数，并让读者就近看到本期核对时间与原稿时间。

当期观察从当前快照按规则计算名次、本期新增星标、总星标与采集时间。项目长期稿内不写「今日第几」等易过期文字。当天可在本地把数字与稿件组合，跨日复用无需再次付费。明确使用 Star（收藏或关注信号）、Fork（仓库分支副本数）的实际含义；没有 Watch、安装、活跃用户、销售或性能数据时，不据此推论订阅量、市场份额和用户动机。[GitHub 星标说明](https://docs.github.com/en/get-started/exploring-projects-on-github/saving-repositories-with-stars)

想进一步判断技术方向，可在单篇质量稳定后，用现有日报做**榜内观察**。先生成一个可核对的离线样表：按北京期号每天只取当前公开版本，记录实际收录数、可分类数、未知数、各类上榜仓库数及新增星标中位数；有旧解读沿用的分类要标资料时间。多日样本按稳定 ID 去重，分别报重复上榜天数、有效期数和缺采日期，缺失涨星不当作零。小样本列举项目，不作增速排名；单个明星项目不能代表整个类别。首期仅做当日及最近最多 7 个自然日的试算，注明分母和覆盖天数，不回溯猜造未采集的日期。公开趋势栏目、周榜、新数据源或宏观导语单独决定。

### 2. 提高真实覆盖，并让降级结果也可读

| 情况 | 生产端处置 | 读者得到什么 |
| --- | --- | --- |
| 当期资料充分 | 复用同规则有效稿或由官方 DeepSeek 单次生成；正文通过校验才进入成功缓存 | 新稿或明确标注的有效复用稿 |
| 上游临时停止，仓库有可信旧稿 | 只按可靠仓库 ID 取稿，原生成时间和版本保留。当前涨星仍取本期 | 旧稿 + 本期事实 + 沿用原因 |
| 无旧稿，仅有可靠简介 | 优先回收本机可追溯、仍可使用的资料。仍不足则显示来源简介、当期数据和明确原因；英文原文如实标来源。可从已核验的中文基础介绍复用一句用途 | 至少可看来源、用途线索和热度；将「有基础资料」与「有完整中文解读」分别统计 |
| 无旧稿而且简介为空，或明确为资料清单 | 仅列可信名称、原始链接、可用指标与资料状态；资料清单沿用默认不付费规则 | 读者知道缺了什么，仍能找到原项目，不凭名字编造用途 |
| 预算不足、AI 关闭、执行繁忙、内容校验失败、用量待核对 | 保留旧稿优先级；无旧稿则回到来源资料。公开原因用固定、通俗的分类；屋主诊断保留更细原因 | 区分「本次未生成」「资料未取得」「结果待核对」，不会把基础介绍标作 AI 新稿 |

维护两个独立事实：**可读内容从哪里来**，以及**本次为什么没有新稿**。目前旧稿回退可能只留下 `STALE`，新设计在任务诊断或兼容的可选字段保留原因；读者无须看内部错误码。读取老 JSON 时字段缺失表示原因未记录。正式库不重写历史。恢复后只在后续获准的发布任务生成新版本；既有快照即使永远缺文也能按来源如实阅读。新增证据不得复活已确认私有、删除或身份冲突的项目资料。

### 3. 具体修复采集和模型输入

- 在采集器、模型与账本边界使用有限枚举，区分单仓库异常、来源级暂停、暂停后未尝试、身份不足、模型未调用、已调用但内容拒收等。保存每次任务的计数、第一处失败环节、可公开的状态码/等待时间。只记确认过的原因，原始响应、凭据、全文和请求头不入日志。
- 独立评估元数据、目录与 README 的成功状态，优先取得解读依赖的资料；目录异常时检查仍能否可靠识别公开仓库并读取 README，分类缺少证据时保留未知。保持串行、同源白名单、单次和任务时限。对真正限流遵守服务端等待时间，权限型 403 不一律标限流，来源级失败后停止本轮补全。下次获准执行优先补有可靠身份但缺文的项目，发布顺序仍按原榜名次。[GitHub REST 请求与限流建议](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)
- 如基线证实重复读取明显，优先复用已验证的 SHA/元数据。条件请求需要同时具备有效校验标记和对应可用内容；收到 304 而本地没有材料时不能宣称资料已恢复。现行规则只在内存中保留 README 正文。若确需跨任务存材料，只提议保存有限摘要、来源和版本，先定容量、有效期、可见性复核及清理；另行评估追加表。第一步不建设全文库、队列或新后台服务。
- 在现有字数总额内，按标题与正文采样，给用途、工作原理、输入输出、适用条件和限制分配空间；跳过导航、徽章、重复安装命令、宣传口号。标题缺失时退回有界的正文首段。README 中的文字视作引用材料；不执行其中的指令，不下载其外链或代码。用夹具覆盖长英文、中文、混合 Markdown/HTML、大段安装说明在前而限制在后的情况。
- 模型一次生成兼容结构；新口径使用独立规则版本，提示与校验共同修改。保留必填字段、长度、重复键、枚举和 JSON 完整性校验。可选内容按明确约定归一化，事实冲突先省略或标源；校验只能验证可判定的约束，文章是否讲清机制须靠对照评审。禁止以填满栏目为由编造数字、对标或缺点。

## 四、按闭环实施与验收

| 顺序 | 改动及交付 | 过关条件 |
| --- | --- | --- |
| 1 · 建立可复现基线 | 在现有 trend 测试根目录建小型脱敏夹具。复现「整批资料缺失、有旧稿／无旧稿」，记录数据流向与调用次数；查能取得的同次安全日志。选取有资料的旧稿作质量对照 | 可离线解释 8/8 快照的两条路径；区分已证实和仍待捕获的首个故障原因。相同输入可重复跑，不接触正式库写入或模型 |
| 2 · 修复资料恢复和缺文分流 | 改采集器、有限原因模型及降级路径；优先解决第 1 步复现的损失点。默认沿用现有日榜接口与获取方式 | 仓库局部故障不拖垮无关项目；上游明确限流后不继续轰击；已取得的有效材料继续可用。预设可恢复场景比旧版多出实际可分析条目，完全断源场景全部得到真实来源与原因 |
| 3 · 编辑规则与证据改版 | 改 README 选段、提示及兼容校验。给 6～8 个项目做新旧稿盲评，覆盖开发工具、基础设施、应用、资料清单、长文及证据不足。至少提供一份正文完整的正例和一份克制的缺资料例 | 按下节量表过关；输出可直接装进现有页面。改规则后旧稿不会被标为新规则生成，分析错误仍可安全发布其余项目 |
| 4 · 贯通发布、兼容和恢复 | 按已验证设计补充可选字段，串起单次任务、仓库缓存、报告归档、公开查询。确有必要时只对现有状态文案和数据绑定做最小适配；如需改变交互或布局，留给单独前端决定 | 老报告、旧缓存、同日重发、重启、回退、新字段缺失和未知枚举有覆盖；同仓并发及收费结果未知不重复请求；公开 GET 始终不触发生成。对 25 个长稿验证报告大小上限和 Redis 回源 |
| 5 · 小样本与正常运行收口 | 离线通过后，再按已有真实样本规则核对预算和可复用验收编号；真实生成另按当时授权执行。记录样本逐项质量、来源、延时、费用及新旧覆盖差异。正常本地启动检查首页→日报→项目→发布台→返回，并合并核对原前端专项第 4 步 | 对账一致；可恢复缺文有生成或可信复用结果，仍缺的能逐项解释；复核正式库和历史均未被试验改写。没有真实模型评审时只标「离线通过」 |
| 后续 · 榜内方向观察 | 在前五步可用后按第三节试算；独立决定是否对读者开放 | 同日重发不重复、样本缺口可见、统计能手算复核，报告准确说明观察范围 |

**质量与覆盖的验收表**（建议门槛，先冻结样本再比较）。

- 每篇五项各 0～2 分：能复述用途与场景、能解释机制及差异、专业细节能回查、关注度表述有依据、限制与推断分清。0 为缺失或错，1 为部分清楚，2 为可独立理解并核对。充分材料的样本目标每篇至少 8/10 且无零项。虚构硬指标、把样例说成实测、把星标说成用户数直接退稿。证据薄弱样本单列，主动说明未知可通过。
- 用同一批材料对照两版，先遮住版本。让非本领域读者读 30 秒后复述对象、用途和结果；技术读者核对一个机制和一个限制。没有真实读者参与时分别记录工程复核和待用户试读，禁止用模型自评充当用户验收。
- 每期按总数和可付费分析数分别记分母：新生成、有效复用、旧稿、仅基础资料、无可用简介、按政策跳过；另列 README 可用率、可分析条目有效中文正文率、校验拒收数、未知用量数。分别记录原始分子/分母和变化原因。把提示文字换掉不会增加完整解读覆盖。离线故障矩阵要求所有条目都能追溯处理路径；真实改善与 11 月 20 日基线并列，注明榜单和外部可用性差异。
- 测试优先扩展 `GithubTrendClientTest`、`TrendInsightCodecTest`、`TrendAiServiceTest`；跨库与预算落到 `TrendAiLedgerIntegrationTest`、`TrendArchiveIntegrationTest`、`TrendHttpAcceptanceTest`，缓存及公开读回归相应测试。Java 运行 `mvn -q compile -DskipTests` 及受影响测试；涉及前端绑定再做构建、静态检查和浏览器验收。

## 五、预算、兼容和回退决定

- 人民币每月 10 元总额继续覆盖手动、定时和真实验收，专属验收保留 0.10 元安排。沿用单并发、每次至多 1,500 输出 token、请求 32 KiB 上限、现行价格配置和按微元预留。先测 25 项最坏报告体积与单次保守费用，再决定是否需要调整篇幅。已知用量即使内容无效仍结算；结果不明保留占用。按同一执行编号与仓库去重，不设自动付费修稿循环。[已有真实验收及预算口径](../operations/trend-g4-acceptance.md)
- 先发兼容读端，再启用新规则写入。新规则只影响后续合规任务；升级不批量刷新已发布历史、不全库付费重算。提议中的轻量中文介绍如需仅凭简介再付费生成，须另定证据版本与防重口径，不能伪造 README SHA 或挤占完整分析预算。
