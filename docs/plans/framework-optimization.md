## 1. 目标和实施边界

1. 先重塑 README。读者能快速了解项目、独立运行起来，贡献者能找到代码归属、验证入口和提交路径。现有有效信息可合并、迁移或保留链接，每项都要能找到。
2. README 完成后先测量，并在动代码前判断哪些架构边界值得调整。只实施有证据的冗余清理和测试优化。结构试点排在后面，按前面的证据决定是否需要。每个修改能独立验收、提交和回退。
3. 冻结仓库声明的框架、依赖、JDK、Node、构建工具和配置版本。保护依赖清单与锁文件、Vite 原有 proxy、alias 和插件，以及本机与生产配置的现有行为。发现已存在的版本声明冲突，先复现并记录，按实际可运行的环境写文档。
4. 保留功能、默认值、路由、API、数据库结构、配置键、权限、会话、限额和浏览器纯算法边界。既有库、空库和隔离测试各走原有安全入口。新增依赖、跨模块重组、生产配置、云资源、远端操作和部署按各自授权处理。

用户要求制定全阶段计划、建立本地分支并交接新会话。新会话先执行 F1，之后用 F2 的评估结果决定 F3～F5 哪些值得做。可以跳过收益不足的改动，F5 的结构变更依据试点方案另行确认。适用验证与提交规则见 [AGENTS.md](../../AGENTS.md)。

## 6. F4 · 测试降本和覆盖保护

- 按普通、隔离集成、浏览器和容量恢复分组，列出断言覆盖的行为、执行入口和失败会发现什么。即使端到端用例与单测涉及同一功能，也要区分算法、序列化、事务、真实存储、浏览器输入和错误恢复所能发现的问题。
- 优先减少准备开销。抽样核对前端重复的 TypeScript 或 Vue 源码转换、模拟和夹具。后端先从同一专项的无状态夹具、重复准备数据和慢测试查起。对并行或上下文复用先验证随机库、Redis 键、清理、端口、事务和浏览器隔离。

- 只在保留下来的用例能覆盖相同条件、失败类型和断言时合并测试。角色矩阵、唯一屋主、会话撤销、额度、审核隐私、并发和回退、Worker 取消与恢复等场景必须可追踪。保留现有普通门禁及显式隔离入口，保护测试发现和条件开关。
- 对拟合并或删除的测试，核对保留用例能捕获原来的独有失败。可复用既有回归样例，必要时在隔离副本验证代表性的失败，再恢复试验改动。共享夹具只抽取准备逻辑，数据库、Redis 状态和故障注入各自隔离。

## 7. F5 · 按需开展单模块结构试点

沿用 F2 的架构决定，只在已找到具体扩展障碍时选一个模块验证。把当前路径和试点路径并排比较，记录涉及的业务目录、共享核心、依赖方向、验证入口和回退步骤。以同一个实际需求或小型变更推演比较，文件搬迁或减少目录数量本身不计收益。

| 边界 | 核对和试点原则 |
| --- | --- |
| 后端 | 逐项核对 Controller、DTO/VO、服务、事务、Mapper 的调用方向。业务规则优先在本模块生长，权限、会话、存储、安全等跨模块核心经已有入口使用。关注 Spring 扫描、代理和 MyBatis 绑定，避免包移动悄悄改变运行行为。 |
| 前端 | 保持路由、API、页面、状态、composable 与算法/Worker 的职责。新增业务可就近放置专属组件、状态和测试，复用现有工具注册入口，保护 `core/` 与 `workers/` 的纯 TS 边界。 |
| 保护核心 | 在已有技术栈内优先用明确入口、可见性、依赖方向与关键契约测试约束访问。保持逻辑可读、边界可查，证明新增业务不必穿过无关模块。对确实反复发生的越界再评估轻量静态检查。 |
| 结构选择 | 以一次小范围变更的依赖方向、涉及目录、测试跨度和回退成本为证据。先评审试点范围，再做可逆试点。包名、模块、构建或部署拓扑需要扩大变更时另行讨论。 |

优先走读低耦合的工具接入路径。当前导航和首页读取 `toolRegistry`，路由侧 `toolViews` 负责懒加载和缺映射检查，默认保留这两个职责。只有试点能进一步降低可验证的改动或失配风险时才调整，保留 Hash 路由、懒加载、分享链接及 Worker 取消隔离。若选择后端试点，检查 `OwnerBootstrapCommand` 的独立 Mapper 扫描及 DTO、查询条件和事务边界。认证、Redis 会话、唯一屋主和审核持久化留作需要独立论证的变更。

**验收。** 试点前给出具体痛点、方案、对照路径与回退点。试点后以既有入口完成构建和相关集成验证，能说明一个类似需求如何更容易接入，以及核心如何保持可追踪。结构收益不明显时，保留当前布局并记录判断。参考 [Spring Boot 代码结构](https://docs.spring.io/spring-boot/reference/using/structuring-your-code.html) 和 [Spring Modulith 的边界验证思路](https://docs.spring.io/spring-modulith/reference/verification.html)，沿用当前依赖。
