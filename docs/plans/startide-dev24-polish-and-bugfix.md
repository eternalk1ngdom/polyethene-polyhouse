## 1. 背景与目标

`dev.24` 连续落地了 3 个跨端闭环（日报新面孔标识与退榜区、发布台自动采集显性状态与 7 日简报自动串联、AI 费用双口径对账与 `017` 迁移）。屋主真机试用第一时间暴露了 **3 类明确问题**，且由于单轮改动量大、尚缺真实宿主机浏览器与真实隔离库联调，需要在合入主线前做一次**系统性的缺陷根治 + 前端视觉精修 + 全局回归巡检**，确保新功能不破坏原有排版质感，也不潜藏并发/状态/边界缺陷。

## 2. 已确认问题与根因分析（来自 2026-11-27 真机截图）

### 问题 A（P0 并发与状态机 Bug · 图二）：发布台误触发「本次更新待确认 + 429 冷却提示」
- **现场表现**：`TrendTaskProgress` 卡片显示灰色 `本次更新待确认` 胶囊，同时底部报错 `请求较频繁或更新正在冷却，请稍后重试。`（HTTP 429）。
- **代码级根因（双重叠加缺陷）**：
  1. **进页 3 并发撞穿后端 `并发=2` 限流闸门**：`TrendConfiguration.trendManagementLimit` 对 `/api/manage/trend/*` 设定的预算为 `30次/分、突发6、并发2`。闭环 2 在 `useTrendOwner.ts` 登录初始化时新增了 `refreshScheduleStatus()`，导致进入发布台瞬间同时并发 **3 个** `/api/manage/trend/*` 请求：
     - `GET /api/manage/trend/fees`（占并发 1）
     - `GET /api/manage/trend/jobs/schedule`（占并发 2）
     - `GET /api/manage/trend/jobs`（若有上次任务记录，占并发 3 → **直接被拦截为 429**！或在刷新过程中点击「更新本期日报」`POST /api/manage/trend/jobs` 同样撞穿 `并发=2`！）
  2. **明确的 429 拒绝错误残留了 `intent`**：`useTrendOwner.ts` 的 `submit()` 在发出请求前就把新建的 `requestId` 写入了 `intent.value` 与 `sessionStorage`；当服务端明确返回 `429`（并发限流或 60 秒冷却，后端必然**未受理**该 `requestId`）或 `400/403` 时，前端未清除 `intent.value`，导致 `TrendTaskProgress` 误以为“请求结果未知”而长期卡在 `本次更新待确认`、主按钮变成 `继续同一次更新`。
  3. **连带联动缺口**：`refreshJob()` 在检测到任务结束后仅自动调用了 `refreshFees()`，未串行刷新 `scheduleStatus` 与 `briefing`，导致刚完成更新后「最近 5 条任务记录」与「7 日风口简报」状态陈旧。

### 问题 B（P1 前端视觉与信息层次 · 图一）：日报条目底部 3 个 Tag 混排怪异且噪音偏高
- **现场表现**：`TrendProjectEntry.vue` 底部 `.meta-tags` 横向依次摆放 `连榜 8 天`（灰胶囊）+ `● Python`（无框圆点文字）+ `AI 智能体`（彩色胶囊），形成“胶囊-文字-胶囊”的割裂夹心感；且前排多为老熟人时，逐条出现 `连榜 8 天` 胶囊造成视觉重复噪音。
- **待敲定重排方案（建议新窗口用 UI/UX 技能复核后择一执行）**：
  - **方案 A（推荐 · 动静分离）**：
    - 底部 `.meta-tags` **完全恢复原版简洁布局**，仅放仓库静态属性：`● 语言` + `分类胶囊`；
    - **强异动信号**（`空降前 5` / `新上榜` / `重回榜单`）放到仓库标题行末尾（随标题一起扫读，真正凸显黑马，符合“突发新面孔”初衷）；
    - **低频降噪信号**（`连榜 N 天` + 可选 `↑N`）改为无边框超轻量纯文本，放到右侧星标胶囊正下方（与今日 `+1,600` 星标组成“右侧动态热度列”，手机端收进底部右对齐或与星标同行），绝不与左侧语言/分类胶囊混排。
  - **方案 B（备选 · 底部显式分组）**：保留在底部元信息区，但将 `● 语言` + `分类胶囊` 放左侧，`连榜` 改为无框轻量文本并以细竖线 `|` 与静态属性分隔；强异动（`空降前 5` / `新上榜`）移至标题旁。
- **顺带语义核对**：前 7 日全勤 + 今日算出 `连榜 8 天` 与读者认知“近 7 日”可能存在轻微认知摩擦，需在新窗口讨论维持 `连榜 8 天` 还是改为 `连榜 7+ 天` / `前 7 日全勤` 文案。

### 问题 C（P1 页面顺序与卡片语言统一 · 图三）：发布台面板顺序倒挂与风格细节微差
- **现场表现**：只读且篇幅较长的「每日自动采集状态（含最近 5 条任务记录）」排在「本次任务」与高频交互的「7 日风口简报」之间，打断屋主核心操作动线；且新写的 `TrendScheduleCard.vue` 在标题字号（`19px` vs 其余三卡 `22px`）、边框色（`#d4e0e4` vs `#c9d8d9`）、内边距（`20px` vs `clamp(18px, 2.4vw, 26px)`）、状态胶囊风格上与 `dev.19` 统一后的其余三卡存在细微割裂。
- **推荐调整方案**：
  - 发布台纵向顺序重排为：**顶部主操作头 → ① 本次任务 → ② 7 日风口简报（高频操作） → ③ 本月 AI 费用（双口径核账） → ④ 每日自动采集状态（只读运维监控 + 最近 5 条记录）**（或把自动采集状态放简报下方、费用上方，新窗口与屋主确认）；
  - 全面对齐四张发布台卡片的容器边框、圆角、内边距、标题 `22px`、`.status-pill` 胶囊位置及按钮尺寸/对齐规范。

1. **星潮开源日报页（`TrendView.vue` / `TrendProjectEntry.vue`）**：

2. **星潮发布台（`TrendOwnerView.vue` / `useTrendOwner.ts` / 4 张子卡片）**：

3. **既有页面零波及回归检查**：
   - 抽查星潮「近 7 日风向」页、单项目详情页、首页、个人中心，确认样式变量、公共按钮/选择框与路由跳转均未受 `dev.24` 改动影响。

### 3.2 后端逻辑、安全与数据口径全局排查
1. **并发与限流策略核对**：评估前端串行化编排即可根治（不放宽后端安全限流预算，保留 `30次/分、突发6、并发2` 的原有防护强度）。
2. **`TrendPresenceCalculator` 与 `TrendReportService` 边界核查**：
   - 核对前 7 天存在同日多版本、跨月/跨年、全榜改名、部分快照损坏、开启 Redis 内容缓存（`TrendReportCache`）时的组合行为；
   - 核对 `GET /api/trend/report` 新增字段体积是否会触及任何响应体或解码上界。
3. **`TrendJobStore.scheduleStatus()` 与 `TrendJobRunner` 边界核查**：
   - 核对数据库仅迁移到 `010～013`（无 `014`/`015`/`017`）、已迁移 `014` 但关闭定时、任务正在执行中、跨北京零点等边界是否全部安全；
   - 核对 `recent(5)` 中若旧任务带有大量 `summary` 计算（当前每条 `job.reportId() != null` 都会调一次 `archive.summary(reportId)`，即 5 条已完成任务可能触发 5 次 JSON 解码！**潜在性能点**：`scheduleStatus()` 里的最近 5 条任务列表前端根本不展示 `summary`，应避免对 5 条历史任务无谓地读取并反序列化 5 份完整日报 JSON！）。
4. **`017_trend_ai_cache_tokens.sql` 与真实隔离库集成测试补课**：
   - 在本机真实 MySQL 隔离库（不碰开发库）中补跑 `017` 正向迁移、双口径写入与汇总、未迁移降级及逆序回退检查；
   - 复查 `TrendAiLedger` / `TrendBriefingLedger` 在 `017` 未迁移时，若事务内执行 `recordCacheUsage` 抛 `BadSqlGrammarException`，在真实 MySQL + Spring `TransactionTemplate` 下是否会触发 `UnexpectedRollbackException`（**高危潜在隐患，务必在真库集成测试中实测核验**！）。
