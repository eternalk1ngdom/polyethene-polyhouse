# 项目架构解耦与可维护性专项评估计划（只读诊断）

创建时间：2026-11-25（Asia/Shanghai）。状态：**待启动（新会话执行，只读评估，严禁修改任何业务源码）**。

## 一、目标与适用范围

对聚妙屋（Polyhouse）当前双端代码仓库（`polyhouse/` Spring Boot 3 + JDK 21 + MyBatis；`polyhouse-web/` Vue 3 + TypeScript + Vite + Element Plus）进行一次系统性的**“架构解耦与 AI 协作友好度”**体检，回答三个核心问题：
1. 哪些地方存在**欠解耦（高耦合）**，改一处容易牵连多处或迫使 AI 一次读取过多无关上下文？
2. 哪些地方存在**过度解耦（过度抽象）**，制造了无实质收益的跳转层或重复模型拷贝？
3. 哪些地方看似扁平或局部重复，实则完全贴合本项目当前规模，**应当明确保持原状、不要乱动**？

## 二、执行铁律（只读边界）

1. **只读评估，禁止改代码**：本阶段只输出诊断报告（经确认后沉淀至 `docs/design/architecture-decoupling-assessment.md`），严禁创建、修改或重构任何业务源码、测试源码、SQL、配置或依赖。
2. **证据驱动，拒绝空话**：指出的每一个问题必须给出真实的文件路径、关键符号名（类/方法/组件/组合函数）与具体依赖链路；未实际读取验证过的文件不得凭目录名臆测。
3. **双向审视，防过度设计**：必须同时排查“欠解耦”与“过度抽象”，避免为了套用设计模式而建议强行加层或抽接口。
4. **结合项目实际规模与既有决策**：执行前先读 [AGENTS.md](../../AGENTS.md)、[DEV_LOG.md](../../DEV_LOG.md)、[framework-assessment.md](../design/framework-assessment.md) 与 [repository-maintenance-backlog.md](repository-maintenance-backlog.md)，尊重已拍板决策（不升级依赖、保留现有三层隔离、`utils/` 纯静态、`core/` 与 `workers/` 纯算法隔离），并与已知延后项（`#7/#8/#9/#11/#12/#13`）对照，不重复立项。
5. **排除非自有产物目录**：扫描时排除 `node_modules/`、`target/`、`dist/`、`.agents/skills/`、`.local-backups/` 及构建缓存。

## 三、六维评估大纲

### 1. 项目结构画像与依赖拓扑
- 梳理 `polyhouse/` 与 `polyhouse-web/` 核心目录及各层的**实际职责**（对照命名与真实行为是否一致）。
- 绘制简明的高层模块依赖流向图（文本箭头，分别覆盖后端包依赖、前端目录依赖及前后端跨端边界）。
- 重点核查拓扑隐患：
  - 模块间是否存在**循环依赖**（双向引用或环状引用）。
  - 底层/公共模块（后端 `common/`、`utils/`、`config/`；前端 `utils/`、`core/`、`api/`、`stores/`）是否反向依赖具体业务模块。
  - 公共目录是否沦为堆放零散业务逻辑的“垃圾桶”。

### 2. 欠解耦（高耦合）热点排查
- **上帝文件 / 巨型组件**：统计全仓自有源码最大文件 Top 5（如超过 500～600 行），逐一拆解其中混杂的不同变化职责。
- **跨边界越权访问**：某业务模块绕过边界直接操作另一模块的内部实现、内部表或内部状态。
- **分层职责错位**：SQL/持久化/第三方 SDK 细节渗入业务核心，或复杂状态机/业务规则过度堆积在 Controller 或巨型 `.vue` 页面组件中（核对 `core/`、`workers/` 与 UI 层的实际边界）。
- **副作用与隐式耦合**：核心计算与 I/O、全局可变状态、环境变量、时钟或隐式调用顺序强绑定的位置。

### 3. 过度解耦（过度抽象）红灯排查
- **透传空壳层**：追踪 2～3 条主业务链路，统计调用跳转层数（Hop Count），识别只做参数原样转发、无实质逻辑的中间层。
- **单实现冗余抽象**：全局仅有一种实现且短期无替换需求，却提前套用接口、工厂、策略或复杂事件机制的位置（结合既有分层约定，区分“合理规范”与“无效复杂度”）。
- **模型转换膨胀**：核查是否存在“新增一个普通字段需同步改 5 个以上相似结构”的情况，区分三层安全隔离的必要映射与冗余拷贝。
- **过早错误抽象**：是否存在把两个本质无关的业务硬塞进同一共享函数/组件、靠大量 boolean 开关勉强兼容的情况。

### 4. 契约边界、跨端一致性与外部依赖隔离
- **边界类型安全**：模块边界、前后端接口、外部 API 响应是否存在无类型黑盒（`any`、无约束 `Map`、裸对象）透传。
- **前后端契约漂移（SSOT）**：核心枚举（角色、审核状态、分类代号、错误码）、校验规则与常量在前后端各自维护的情况；区分必要的“前后端双重防线”与容易同步漏改的“重复事实源”。
- **外部依赖防腐**：GitHub 抓取、DeepSeek AI 调用、MySQL/Redis 特殊脚本、IndexedDB/BroadcastChannel 等外部/宿主依赖是否收敛在清晰适配层，还是散落在业务文件中。

### 5. AI 协作友好度压力测试（基于真实场景推演）
选取聚妙屋 **2 个代表性真实场景**（1 个跨端核心业务 + 1 个纯前端工具）实际追踪源码并量化：
- **场景 A（跨端业务）**：例如「星潮 7 日窗口统计与简报」或「个人空间资料审核/卡面」——若让 AI 新增一个展示字段或扩展一条新规则，最少需要阅读和修改多少个文件？核心摩擦点在哪里？
- **场景 B（纯前端工具）**：例如「妙替（PolyReplace）」或「妙压（TargetKB）」——若删掉某核心模块的内部实现、仅保留其外部契约，AI 能否在不改动其他模块的前提下独立重写？卡点在哪里？

### 6. 综合评分与按 ROI 分级的行动清单
1. **五维健康度速览表**：对【边界拓扑 / 分层深度 / 契约清晰度 / 微观内聚 / 防过度设计】给出评级（健康 / 轻度警告 / 高风险）及一句话证据依据，并附上关键量化数据（最大文件 Top 5 行数、主链路平均跳转层数、单次变更触达文件数）。
2. **分级整改建议（按投入产出比排序，并与既有延后项对齐）**：
   - **P0（高风险，优先止血，限 3 项以内）**：真正阻碍迭代、改一次易引发连锁 Bug 的耦合点，写明最小改法、影响面与预期收益。
   - **P1（中优先级，随后续迭代顺手重构）**：无需专门停工大改，下次触碰该模块时顺势拆分。
   - **明确保留项（不要乱动）**：明确肯定当前已解耦得当、或看似扁平/重复但完全契合当前规模、**不建议重构**的区域。
