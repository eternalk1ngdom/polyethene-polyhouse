## 2. 本地核对结果与需要调整的旧计划

以下保留计划编制时的实现基线；P1/P2 已补充 ADMIN、改密、凭据版本及屋主开户，最新交付见第 8、12 节，其他旧计划调整仍按已批准范围执行。

- 现有角色只有 `USER`、`INSIDER`、`OWNER`。`INSIDER` 是特邀熟人/高开销功能资格，不是管理员；前后端资料类型、JWT 解析及显示都尚无 `ADMIN`。
- `UserRoleEnum.hasPermission` 按权重比较，`AuthInterceptor` 用它处理 `@RequireRole`；直接增加一个管理员权重并用“达到 ADMIN”判断，会误让更高权重的 INSIDER 获得管理能力。
- `AuthController` 的注册方法当前跳过 Bearer 验证；`AuthServiceImpl.register` 固定创建 USER。不能把角色选择直接加进原公开 `RegisterDTO` 而保留匿名创建。
- `sys_user.username` 已有唯一索引，主键使用雪花 ID；`sys_user.status` 与 `deleted` 分别表示停用和软删除。现有账号的名称、ID、屋主唯一槽位和成长数据不应为统一格式批量重写。
- 登录验证与会话检查会读取当前数据库账号状态；`AuthRedisStore` 支持精确撤销 PC/H5/PLUGIN 的全部会话。当前没有改密接口，也没有保证“修改密码后旧 Token 永久失效”的凭据版本字段。
- `AvatarService.upload` 当前提交即更新头像；`AvatarWebConfig` 提供公开静态图片及一天缓存。审核需要独立待审存储和发布步骤；前端 `AvatarChange` 响应解析也需同步改动。
- 个人资料目前不能修改昵称，注册时可以指定昵称；留言未实现。旧计划的“仅命令开户、昵称不可编辑”由本次“屋主页开户、用户可申请修改昵称”的新需求替代。
- 根目录策划书只读。批准后已精准更新 AGENTS 的角色边界和计划目录；实际枚举、授权代码及测试仍待 P1 实现。修改前核对 AGENTS 工作区内容经 Git 规范化后的哈希与 HEAD 一致，未混入其他内容改动；不覆盖未归属文件。

## 3. 已批准的角色与管理边界

### 3.1 独立 ADMIN，保留 INSIDER

- `USER`：普通使用者；`INSIDER`：保留现有高开销资格；`ADMIN`：账号管理协助者；`OWNER`：唯一屋主。
- ADMIN 权重为 30，原 USER=10、INSIDER=50、OWNER=99 不变。该数字仅服务已有分级机制，**不是管理权限的充分条件**，业务不使用数字字面量比较。
- 管理能力使用明确的角色集合/业务策略检查，例如只有 ADMIN/OWNER 能进入账号管理，只有 OWNER 能开户和审核。INSIDER 即使权重大于 ADMIN，也没有封禁或审核权。
- 现有高开销/收费功能保持 INSIDER/OWNER 资格；管理员身份本身不自动获得这类权限。以后若需要同时具备管理和高开销资格，再独立讨论能力组合，本阶段不引入完整 RBAC 权限平台。
- AGENTS 第 4 条已澄清适用边界：基础账号/资料管理按本次明确角色授权；高开销/收费能力仍保留 INSIDER 闸门。不能在 ADMIN 接口上只加 INSIDER 门槛，导致 ADMIN 无法使用或 INSIDER 意外成为管理员。
- 创建表单不能创建 OWNER 或选择任意角色字符串；OWNER 仍由已有专门初始化流程和数据库唯一约束管理。首版不开放创建 INSIDER、角色任意编辑或屋主转让。

## 4. 已批准的用户流程与具体规则

### 4.1 屋主创建账号

1. 屋主登录，在专属管理区进入“创建账号”，选择普通用户/管理员；普通用户为默认项。
2. 登录账号、默认昵称与初始密码均由服务端生成。表单展示账号格式说明，提交前不把某个“预计编号”承诺为已保留编号。
3. 账号格式为 `ph000001`、`ph000002`；默认昵称为“小屋住户000001”。达到六位以上自然扩展，禁止截断；S7 已确认。
4. 使用 MySQL 独立发号记录加行锁，与用户创建事务配合；唯一索引兜底。不能在线查询最大编号后简单加一，也不能只在浏览器/单 JVM 内计数。
5. 成功分配过的登录账号在封禁、注销后不回收；允许断号，不承诺连续无缺口。旧自定义账号保持原名，新发号不得撞上历史/软删除记录；迁移时明确初值和碰撞处理，不自动重命名旧账号。
6. 每账号使用安全随机源生成 20 位 ASCII 初始密码，符合现有 BCrypt 的 72 字节限制；不使用所有人共享的默认密码，不从序号/日期/用户名推导密码。
7. 成功页只向本次 OWNER 展示一次账号与初始密码，支持主动复制并确认已保存；响应不缓存，明文不写日志、localStorage、审计记录或数据库。数据库只保存 BCrypt 哈希，后台以后也无法查看原密码。
8. 使用创建请求编号防止重复点击或网络重试生成多个账号。响应丢失时可以确认是否已建成，但不能重新查回初始明文；由屋主显式重置为新的临时密码（S6 已批准）。
9. 屋主通过私密渠道交付给本人。创建管理员账号时也不能跳过同样的凭据规则、目标角色白名单和审核机制。

### 4.2 首次使用与修改密码

- 新账号标记为“必须修改初始密码”（S3 已批准）。首次登录获得受限会话，仅允许必要的本人资料读取、改密和退出；后端同样限制受保护业务、管理与审核操作，不能仅前端跳转。
- 初始密码登录后修改密码，沿用“当前密码 + 新密码 + 前端确认新密码”；服务端验证当前密码、新密码规则及会话，拒绝与当前密码相同的新密码。密码不自动裁剪空格。
- 成功改密后撤销本人全部终端会话，清理当前客户端会话，要求重新登录。密码变化本身不是公开内容，不需要屋主审批；屋主不能查看用户自己设置的密码。
- 现有正常账号不强制套用“首次改密”，避免把真实屋主锁在管理入口外；只对新创建或显式重置的账号设置标记。
- 为避免数据库/Redis 部分成功和后续解封导致旧 Token 复活，新增持久化的凭据/会话版本：JWT 携带版本，认证时核对数据库版本。改密、重置、封禁等操作增加版本并撤销 Redis 会话；旧会话不能被重新认可。
- 凭据更新、版本更新和审计在同一数据库事务，Redis 会话按既有用户行锁纪律撤销；失败返回明确结果，不宣称 MySQL/Redis 是一个原子事务。已经撤销的会话不恢复，必要时重新登录；超时不自动重发改密。
- 登录、改密、封禁、注销和审核写操作要重新核对最新状态，关键行使用稳定加锁顺序，防止旧认证快照越权或多用户锁死锁。对于已经在执行的请求，不承诺无条件追溯取消。
- 当前原始 JWT 没有版本字段。迁移首选增加可空版本声明的过渡读取：只有数据库版本为初始值的旧账号可暂时接受原 Token；一旦改密/封禁使版本变化就永久拒绝原 Token，后续正常登录签发带版本的新 Token。实现前补测试并明确窗口，不偷偷令全体用户失效。

### 4.3 用户修改昵称与头像

- 用户在个人中心自行提交新昵称，与不可修改的登录账号分开；昵称仍限制 1～32 字符，并限制控制字符、只用纯文本展示。不可将角色、状态或用户 ID 混入资料更新 DTO。
- 为衔接此前“公开信息先审后上”的要求，昵称同头像一样先提交审核（S4 已批准）。用户看到自己的待审内容与状态，其他展示继续使用上一次批准值；“可以自己修改”体现为可以自主提交，无需屋主代填。
- 默认昵称由系统生成，可作为初始已确认内容；已有昵称和头像不能自动算成已审，先生成待核对清单，由屋主确认保留或撤下，不批量重置真实屋主。
- 每种资料最多保留一份有效待审版本，新提交替代旧待审；审核必须针对精确提交版本，旧审核不能覆盖新申请。头像每日提交最多 5 次、昵称每日最多 2 次（S8 已批准），自然日沿用 Asia/Shanghai；失败/回滚和重试的计数语义实现时说明。
- 图片继续裁剪与重新编码，待审文件进入独立私有目录；本人及 OWNER 通过鉴权接口预览，不提供匿名直链。批准后再生成公开文件地址并更新当前头像；驳回保留原展示，废弃文件按安全队列清理。
- 头像删除/下架改为默认头像并移除源文件引用；已下载或浏览器缓存副本不能保证立即消失。昵称下架恢复系统默认昵称或先前明确批准值，选择及记录要可追溯。
- 仅 OWNER 审核；OWNER 自己提交的昵称/头像也走同一流程，可以由 OWNER 显式批准，不因为角色高就自动公开。
- 被封禁/软注销账号不能继续提交，旧待审也不能在账号失效后发布。头像缓存、会话多标签页和旧请求回调继续遵守现有防乱序机制。

拟定申请状态为待审核、已通过、已驳回、已被新提交替代、已失效。只有仍为待审核且目标账号可用的对应版本能通过/驳回；终态不能重复发布。历史“已通过”记录保留审批事实，当前展示字段另行指向正在生效的内容，下架不能篡改历史审批事实。

### 4.4 封禁、解封与密码找回

- 封禁使用 `status=0`，保留原账号、数据与审计；不使用 `deleted=1` 假装封禁，也不把封禁等同于永久数据删除。
- 管理员仅能对当前角色为 USER 的目标执行封禁；不能封禁另一个管理员、INSIDER、OWNER 或自己。屋主可封禁其他非 OWNER 账号。
- 操作弹窗明确显示账号、昵称、角色和动作，填写原因后确认；后端在事务内重新检查操作者权限、会话及目标最新角色，不采信前端判断。
- 首版不开放普通用户/管理员角色互相转换。若目标通过受控途径已经发生变化，旧列表操作需要重新核对当前角色并拒绝过期修改，不能按创建时角色授权。
- 封禁增加目标会话版本并撤销所有支持终端；已登录用户后续受保护请求失败，不能仅禁止下一次密码登录。解除封禁也不能恢复历史 Token。
- 首版只由 OWNER 解封（S5 已批准），避免管理员撤销屋主的处置；不做自动到期封禁任务，暂按封禁/解封两个明确操作管理。
- OWNER 可为非 OWNER 重置临时密码（S6 已批准），用于朋友忘记密码或初始交付丢失；不开放匿名找回、不引入短信/邮箱费用，管理员没有此权限。重置要求撤销旧会话、强制再次改密，不能查询原密码。
- 屋主自身无法登录时采用专门的受控运维恢复流程；网页管理者不能重置 OWNER。完整屋主恢复脚本本阶段不默认新增，部署前明确人工恢复预案。

## 5. 管理页面与个人中心组织

采用同一套管理布局、两种授权视图，减少两份页面逻辑；对用户分别显示“管理中心”和“屋主工作台”。路由/组件/API 模块按职责拆分，保留当前白底/墨色风格和现有 Element Plus。

| 区域 | 普通用户/特邀熟人 | 管理员 | 屋主 |
| --- | --- | --- | --- |
| 个人中心 | 当前昵称/头像、待审状态、申请修改、修改密码 | 同左 | 同左 |
| 账号管理 | 无入口 | USER 列表、筛选、封禁确认 | 非 OWNER 账号列表、创建 USER/ADMIN、封禁、解封及重置密码 |
| 资源审核 | 无入口 | 无入口 | 昵称/头像待审列表、私有预览、通过/驳回、发布内容下架 |
| 操作记录 | 无管理入口 | 按必要范围显示自己的操作反馈 | 查看最小审计列表，查询页面可在本阶段内后置交付 |

- 页面有加载、空列表、失败重试和提交中反馈；分页查询限制最大页大小，不一次加载全库和全部图片。
- 管理员列表只返回权限范围内的必要字段；不向其交付密码哈希、原密码、完整扩展 JSON、登录 IP 或其他不需要的信息。
- 用户 ID 在前后端保持字符串传递。筛选/排序字段使用白名单，列表与单条查询均验证目标范围，不能用前端筛选隐藏泄露。
- 重要操作只在服务端确认成功后更新页面；冲突要求刷新，不把 HTTP 200 或按钮点下当成业务成功。
- 表单标签、键盘焦点和错误位置明确；移动端可以卡片显示列表，不为小量内测提前加入大表格虚拟化和数据图表。
- 已使用 UI/UX Pro Max 只读查询核对危险操作确认和反馈。设计系统/产品搜索返回营销或分析面板建议，与本项目不完全匹配，未照搬其色彩、外部字体、图标库或 Vue 表单依赖；沿用工程现有组件和样式。

### 6.1 后端边界

| 拟定职责 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| 管理授权策略 | 判断操作者、动作、目标角色和状态 | 不直接更新用户资料或文件 |
| 账号供应服务 | 发号、生成初始凭据、创建幂等、防重复开户 | 不承担昵称/头像审核 |
| 账号安全服务 | 本人改密、会话版本、初始改密状态及屋主重置 | 不输出已存密码或承担账号列表查询 |
| 账号管理服务 | 分页投影、封禁/解封、目标范围核对 | 不修改成长余额或赋予 OWNER |
| 资料审核服务 | 昵称/头像提交版本、审批状态、发布/下架及文件补偿 | 不引入通用工作流引擎或社区系统 |
| 审计记录 | 保存操作者、目标、动作、结果、时间与安全原因 | 不保存密码、Token、图片字节或完整请求体 |

沿用 Controller → Service → Mapper 分层；DTO 使用 Jakarta Validation，VO 明确投影，统一 Result。凭据交付只使用专门一次性响应，普通用户资料 VO 和列表 VO 不包含凭据。utils 只做无状态运算，不注入数据库或 Redis。

### 6.2 HTTP 契约候选

| 候选入口 | 权限与效果 |
| --- | --- |
| 原 `POST /api/auth/register` | 保留明确的关闭响应，不新增账号；不改成匿名可选角色接口 |
| `POST /api/manage/accounts`（P2 已实现） | OWNER；目标角色、创建请求编号及 ADMIN 必需的屋主当前密码；服务端生成账号/昵称/密码 |
| `GET /api/manage/accounts/creation`（P2 已实现） | OWNER；用 requestId 核对自己的创建事实，不取回初始密码 |
| `GET /api/manage/accounts` | ADMIN/OWNER；分页字段白名单，服务端限定可见目标 |
| `POST /api/manage/accounts/{id}/ban` | ADMIN 仅 USER，OWNER 仅非 OWNER；原因及并发版本校验 |
| `POST /api/manage/accounts/{id}/unban` | 仅 OWNER，S5 已批准；不恢复历史会话 |
| `POST /api/auth/password/change` | 当前本人；验证旧密码，改密后全部终端退出；受限首次会话可用 |
| `POST /api/manage/accounts/{id}/password/reset` | 仅 OWNER，目标非 OWNER，S6 已批准；单次交付新临时凭据 |
| `POST /api/auth/nickname/submissions` | 当前本人；新增昵称审核申请，S4 已批准 |
| 原 `POST /api/auth/avatar` | 当前本人；上传改为返回申请编号/状态/额度，不再返回已经生效的新头像 |
| `GET /api/auth/profile-submissions` | 本人申请状态和必要原因，不返回他人申请 |
| `GET /api/manage/profile-reviews` | 仅 OWNER；昵称/头像待审分页，不返回敏感文件路径 |
| `GET /api/profile-submissions/{id}/image` | 仅头像提交本人/OWNER；认证后返回图片字节，禁止缓存为公开资源 |
| `POST /api/manage/profile-reviews/{id}/decision` | 仅 OWNER；精确版本的通过/驳回，原因校验 |
| `POST /api/manage/accounts/{id}/profile/takedown` | 仅 OWNER；下架已发布昵称/头像，记录明确目标字段 |

私有图片为鉴权后的二进制资源响应，沿用现有媒体响应的合理例外，不返回 Entity；错误仍使用统一错误语义。普通 `<img>` 不会自动附带存储中的 Bearer Token，前端需通过鉴权请求读取 Blob 并管理对象 URL 释放。

修改 avatar 响应是一次前后端契约变更，必须同一闭环更新客户端解析与测试；目前尚未线上发布，但不能假设旧页面同时刷新。升级后旧请求不得得到“已发布”假提示，必要时提示刷新页面。

## 7. 数据迁移与一致性设计

以下是数据职责设计。P1 已追加 `005_account_security.sql`：用户凭据版本、首次改密标记与最小成功改密审计；P2 已追加 `006_account_provisioning.sql` 的发号/创建事实表；其他记录尚未建表，实际表名/字段和迁移编号在对应模块编码前确认；现有 `001`～`004` 迁移不重写。

| 数据位置 | 拟增内容 | 原因 |
| --- | --- | --- |
| sys_user | 会话/凭据版本、首次改密标记，视方案增加账户管理并发版本 | 阻止旧 Token 复活，区分初始凭据，并发修改不覆盖新状态 |
| 发号记录 | 账号类型、下一序号/已分配序号 | 数据库层串行发号，不靠前端或 Redis 持久保存身份序列 |
| 账号创建请求 | 请求编号、操作者、目标、结果；不保存明文初始密码 | 幂等开户和响应丢失后的结果核对 |
| 资料申请记录 | 用户、类型、提交版本、待审昵称/私有文件键、状态、时间、审核人和原因 | 区分待审与公开内容，防止重复/过期审核 |
| 审计记录 | 操作者 ID/角色快照、目标、动作、结果、时间与安全原因 | 管理操作可追溯；需限制记录大小、保留期和读取范围 |

- 索引围绕账号唯一、创建请求唯一、申请用户/类型/状态、审核时间及管理查询设计；保留 owner_slot 唯一保障，不自动回填第二个屋主。
- MySQL 不保存图片字节；公开图片与私有待审图片使用不同目录，容量与清理各有上限。事务失败清理未引用新文件，发布成功再清理被替代旧图；结果未知时不能误删可能已提交的文件。
- 审核需要同时核对操作者和目标，事务使用确定的用户加锁顺序，避免与封禁/改密/注销交叉死锁；操作前的页面资料不能替代锁内最新身份和状态检查。
- 一次头像审批需要更新对应字段和申请状态，不能将整份旧 User 回写而覆盖经验、硬币、角色或其他设置；昵称与头像申请相互隔离。
- 新迁移默认保留已有账号的名称、密码哈希和可用状态；历史内容核对由明确确认的清单驱动。真实数据先备份，不在启动时自动改表、批量改名或清空会话。
- 包含 ADMIN 后，旧后端枚举/旧前端解码器不能完整理解新数据。因此旧代码回退存在兼容限制：在产生 ADMIN 或启用新会话规则前先演练；不能承诺任意切回原版本仍安全。异常时优先关闭管理写入口、使用兼容修复版本；数据回退需要独立恢复步骤。

| 步骤 | 工作 | 独立交付与验收条件 |

| P4 资料审核闭环 | 头像私有待审与审核发布、昵称申请、本人状态、OWNER 审核及下架页面 | 所有待审内容不提前公开；重复/旧审核与失败补偿正确；旧公开资料迁移核对有记录 |

P1 的安全服务与个人中心改密同一闭环交付；P2 的注册关闭、开户接口与屋主表单同一闭环交付，避免长时间停在“注册关了但屋主也无法开户”。新建账号前必须已具备可用的首次改密流程，不能生成无页面可用的强制改密账号。

## 9. 验收清单

### 9.1 权限与开户

- 匿名请求旧注册路径、伪造角色或直接调用开户接口均不创建用户；USER/INSIDER/ADMIN 无法代开户。
- OWNER 只能选择 USER/ADMIN，不能提交 OWNER、未知角色或额外用户 ID/用户名/成长字段来覆盖服务端规则。
- 并发开户、多次点击、响应超时、账号唯一冲突和数据库异常都不重复发放同一身份；不回收已使用账号名，不重命名历史账号。
- 初始凭据不出现在日志、列表接口、历史查询、浏览器持久缓存或数据库明文字段；页面关闭后不能查询回来。

### 9.2 密码与会话

- 错误当前密码、超长字节、空白规则边界、重复新密码和非法初始改密绕过都拒绝；不恢复此前已取消的“连错五次锁定”机制。
- 改密/重置前 PC/H5/PLUGIN 的旧 Token 在更新后均不可用，重新登录只接受新密码；Redis 故障、数据库回滚、提交结果未知不伪报成功。
- 受限首次会话不能调用管理、审核和其他受保护写入口；前端绕过跳转无效；真实既有屋主不会被强制套用新账号流程。
- 密码变化与并发登录、封禁、解封、注销及多标签页旧响应组合测试通过；已撤销 Token 不因恢复状态而复活。

### 9.3 封禁与审核

- ADMIN 只能看到/封禁 USER；修改目标编号、筛选参数或目标角色在处理中变化也不能越权。INSIDER 没有管理员权限。
- OWNER 可以封禁 ADMIN/INSIDER，但不能封禁自己、注销自己或从网页生成另一 OWNER；解封与重置按最终批准矩阵验证。
- 待审头像匿名直链拒绝、本人/OWNER 可预览、其他登录用户不能预览；目录穿越、符号链接和隐藏清理记录继续拒绝。
- 提交/通过/驳回/替代/下架、版本冲突、重复审核、账号失效、磁盘错误、提交回滚、废弃文件清理及配额通过。
- 昵称审核前公共展示不变化，显示以纯文本处理；头像与昵称审核不会互相覆盖，也不覆盖成长和角色。

### 9.4 回归与运行边界

- 每步实际执行 `mvn -q compile -DskipTests`、`npm run build` 及相关有意义定向测试；阶段末运行统一普通验收，避免反复为同一未变基线全量重测。
- 浏览器检查 OWNER 开户/审核、ADMIN 封禁、USER 改密/提交资料与确认失效反馈；不把接口测试成功代替页面对接验收。
- 保留妙替文件本地处理、预览与 ZIP 下载，登录/成长每日防重、退出、软注销和 ThreadLocal 清理继续有效。
- 使用独立测试库或精确随机夹具；已有正式 OWNER 的本机开发库禁止运行含 OWNER 夹具的默认全量实例测试，不触碰真实初始化记录。
- 本阶段不自动操作朋友服务器，不自动推 GitHub，不创建发布标签；部署时另行核对机器当前资源、平台适用要求和加密访问方式。

## 10. 已批准的 S1～S9 决定

用户已于 2026-10-29 明确全部批准以下推荐值，全部纳入本阶段实施范围，不再重复询问。它们是目标行为，不是已实现能力；范围变化时在本计划记录新的用户决定。

| 编号 | 已确认事项 | 采用值与理由 |
| --- | --- | --- |
| S1 | 管理员与 INSIDER 的关系 | 新增 ADMIN，权重 30，管理用精确角色策略；保留 INSIDER 的既有高开销资格，避免好友自动成为管理员或管理员自动拥有费用权限 |
| S2 | “默认密码”采用统一值还是每账号生成 | 每账号独立随机 20 位，单次交付；统一密码会使任一接收者可能登录其他未改密账号 |
| S3 | 是否首次登录必须改密 | 是；临时密码只用于交接，新建/重置账号首次会话受限，既有真实账号不受强制迁移影响 |
| S4 | 用户昵称修改如何审核 | 用户自主提交，OWNER 通过后公开；与头像保持先审后发，避免新增可绕过审核的文本入口 |
| S5 | 是否补解封及权限 | 补上，仅 OWNER 解封，避免管理员撤销屋主处置；暂不做定时封禁 |
| S6 | 是否补忘记密码的处置 | OWNER 可重置非 OWNER 临时密码，要求再次改密；不做短信/邮箱找回，管理员不能重置他人 |
| S7 | 账号/默认昵称格式 | `ph000001` 起、默认“小屋住户000001”；名称不可自改、昵称可申请修改，保留历史自定义账号 |
| S8 | 提交审核频率 | 头像每日 5 次、昵称每日 2 次，每种内容一份有效待审；限制反复申请和磁盘占用 |
| S9 | 审计与高风险操作确认 | 保存最小操作审计；创建 ADMIN、重置密码及封禁管理账号时再次验证屋主当前密码；不额外引入 MFA 服务 |

首次改密、会话版本、审核待审隔离、并发目标权限检查是相应安全行为的实现配套，不会只实现页面提示就宣称完成。S9 的审计保存与审计查询页面分别验收，查询页可后置；不记录凭据或完整提交图片。
