## T1 实施与数据流

- `core/targetKbCompress.ts` 是不可变状态机：`startSearch` 先以质量 1.0 试一次，`advanceSearch` 依据实测字节数二分并返回下一次试探、成功或失败。只以"不超过上限"为约束求最大质量，低于下限交给 COM 段补齐——区间搜索在"最高质量仍小于下限"时会无解，补齐才是正确出口。
- 尺寸降档按 0.85 连乘、最多 6 档、最短边 64px；无法再缩时返回 `failed`，**不返回超限文件**，也不静默交付一个"差不多"的结果。
- `core/jpegComInjector.ts` 只解析 SOS 之前的段，遇 SOS/EOI 停止，避免把熵编码数据误判为标记；补齐段插在头部元数据（APPn 与 COM）之后，保证 JFIF 仍是第一个段。差额 1～4 字节无法精确补齐，返回未满足而不是写出超限文件。
- DPI 只写 JFIF APP0：有则原地改写密度（长度不变），无则插入 18 字节段；不伪造 EXIF。改写与补齐都返回新数组，不修改入参。
- 三个模块均为纯函数：不建 Canvas、不读文件、不引用 Vue 或 Element Plus，符合铁律 7。测试用假编码器与合成 JPEG 段，因此能覆盖搜索逻辑与字节布局，但不能证明真实编码的体积收敛。

## T2 实施与数据流

- `core/targetKbSource.ts`：输入上限检查。复用 `avatarCrop.ts` 的 `avatarSourceSize()` 解析 JPEG SOF 与 PNG IHDR，不重写段解析；先查 20 MiB 文件体积（零成本），再查 40 MP 像素数。WebP/AVIF 解析不出尺寸时**不拒绝**，退回解码后 `checkDecodedPixels()` 补检——这一步已付出解码内存，属降级路径。另含 `fitWithinLongEdge()` 等比缩放：放这里是为了能在 Node 测试，Worker 不自带几何逻辑。
- `core/targetKbProtocol.ts`：请求带递增 `id`，`encode` 携带字节、目标区间、`allowShrink`、`dpi`；`cancel` 只带 id。`isCurrentReply(replyId, activeId)` 判断回调归属，`activeId = 0` 表示"没有有效任务"，此时任何回复都丢弃。`parseRequest()` 逐字段校验（结构化克隆不带类型信息），目标区间直接复用内核 `createTargetRange()`，不另立一套上下限。
- `workers/targetkb.worker.ts`：`inspectSource` → `createImageBitmap` → 内核二分（每次 probe 一次 `OffscreenCanvas.convertToBlob`）→ 写 DPI → COM 补齐。quality 完全由内核给出，Worker 不自行调整。
- 顺序约束：**先写 DPI 再补齐**。原图没有 JFIF APP0 时 `rewriteJfifDpi()` 会新增 18 字节，颠倒顺序会让补齐后的最终体积超出目标。
- 内存与正确性：只保留"满足上限"的编码结果（最终采用的必在其中），最多 12 份；透明图先铺白底，避免 PNG 转 JPEG 得到黑底。
- 取消与过期隔离：与妙替同一思路但下沉一层。妙替把 `revision + terminate` 放在视图层，妙压 T2 没有页面，所以 id 校验放在协议与 Worker——新请求到达即改写 `activeId`，正在跑的任务在每个 probe 前比对，发现被作废就静默退出；`cancel` 只清 `activeId`，不终止线程。妙替的协议与 worker 未改动。

## 本轮验证

自动化（T1 23 项 + T2 16 项）：

- `node --test tests/target-kb-*.test.mjs`：39 项通过。T2 新增 16 项：输入上限与缩放 8 项（20 MiB 边界、40 MP 边界、PNG IHDR、WebP 不拒绝、解码后补检、等比缩放）、协议 8 项（id 校验、过期判定、目标区间、DPI、`allowShrink` 缺失）。
- `npm test`：174 通过 / 0 失败（基线 158 + 新增 16）；`npm run lint:check` 退出 0；`npm run build`（含 `vue-tsc`）退出 0。
- 构建首次失败 1 项：`new Blob([bytes])` 的 `Uint8Array<ArrayBufferLike>` 不可赋给 `BlobPart`。改为把形参标注成 `Uint8Array<ArrayBuffer>` 并注明原因，没有用断言绕过。

真实浏览器（Chrome 156.0.8078.79 headless，Windows 本机，临时验收页经 Vite dev 直接加载 `workers/targetkb.worker.ts`）：

| 样本 | 输入 | 目标 | 编码次数 | 结果 | 耗时 |
| --- | --- | --- | --- | --- | --- |
| 高分辨率 6400×4000 | 1,389,605 B | 120 KiB | 33（降档 2 次：6400→5440→4624） | q=0.2143，122,745 B，4624×2890 | 7.4 s |
| 手机照 3840×2400 | 1,602,752 B | 500 KiB | 11 | q=0.8849，503,959 B，3840×2400，DPI 300 写入成功 | 0.96 s |
| 小图 280×175 | 23,615 B | 60～100 KiB | 1 | q=1.0 得 48,621 B，补 COM 12,819 B 后 **恰好 61,440 B** | 5 ms |

- 逐次 probe 的质量与字节已记录：手机照 1.000→2,892,549 B、0.550→239,975、0.775→356,193、0.887→523,056（超限）……0.8849→503,959（采用）；高分辨率每档都先以 q=1.0 试一次，再二分到该档最低质量仍超限才降档。
- 三个输出都用真实解码器复核：`createImageBitmap` 可解码、尺寸正确、末两字节为 EOI。补齐文件另用系统看图器（WPS 图片）打开正常，浏览器渲染截图无破图——字节测试证明不了"能打开"，这一步单独做了。
- 过期与取消：提交新任务后，旧任务 0 条回复（`staleReplies: 0`）；`cancel` 后该任务 0 条回复。
- 超限路径：把 SOF 尺寸改成 9000×5000（42.9 MP）→ 1 ms 内 `pixels-too-large`（**解码前**拦截）；补零到 21 MiB → 13 ms 内 `file-too-large`。
- 样本来源：工作区无 JPEG、本机无外网（curl 与 fetch 均被拦），改用 Windows 自带真实照片（`C:\Windows\Web` 的 Spotlight 与锁屏图），只放 gitignored 的 `polyhouse/target/targetkb-fixtures/`，验收后已删除。**不是 CC0 素材**，因此不进版本库、不对外分发。
- 未验证：Safari/Firefox/移动端；T3 页面交互与布局；WebP/AVIF 的真实文件（只验了"解析不出不拒绝"与降级函数本身）；真实 42 MP 照片（超限用改头文件验证，因为拦截发生在解码前）；带透明通道 PNG 转 JPEG 的白底效果（代码已铺白底，但无真实样本）。无后端改动不运行 Maven。

## 未完成与风险

- T3～T5 未获批准；`toolRegistry` 仍是 `planned`，页面仍是占位，**用户看不到任何新功能**。
- 25.6 MP 单图最坏 33 次编码、约 7.4 秒：T1 的"每档固定 12 次上限"在降档后仍会跑满，T3 需要进度反馈，否则用户会以为卡死。
- 观察到 q=1.0 的字节数**不随尺寸单调下降**（6400 宽 3.72 MB，5440 宽反而 5.71 MB，高质量重采样引入高频）。搜索仍收敛，但降档后首次 q=1.0 试探常是浪费的一次编码；本轮未改内核，留待 T4 评估是否先试探低质量。
- DPI 写入依赖编码器自带 JFIF APP0（Chrome 的 `convertToBlob` 恒有，实测三个输出都带 APP0），因此改写长度不变；若将来换编码器不写 APP0，插入的 18 字节会让"刚好等于上限"的结果超出 18 字节，届时需在写 DPI 后补一次校验。
- `ui-ux-pro-max` 以 junction 方式挂载，能否被自动识别需重启后实测；未复制任何文件，73 文件散列清单与停用流程不受影响。
- 妙压合并前需先把本分支 rebase 到含 dev.10 的基线，届时 `DEV_LOG.md` 与 `docs/plans/README.md` 需要人工核对一次。
