## T1 实施与数据流

- `core/targetKbCompress.ts` 是不可变状态机：`startSearch` 先以质量 1.0 试一次，`advanceSearch` 依据实测字节数二分并返回下一次试探、成功或失败。只以"不超过上限"为约束求最大质量，低于下限交给 COM 段补齐——区间搜索在"最高质量仍小于下限"时会无解，补齐才是正确出口。
- 尺寸降档按 0.85 连乘、最多 6 档、最短边 64px；无法再缩时返回 `failed`，**不返回超限文件**，也不静默交付一个"差不多"的结果。
- `core/jpegComInjector.ts` 只解析 SOS 之前的段，遇 SOS/EOI 停止，避免把熵编码数据误判为标记；补齐段插在头部元数据（APPn 与 COM）之后，保证 JFIF 仍是第一个段。差额 1～4 字节无法精确补齐，返回未满足而不是写出超限文件。
- DPI 只写 JFIF APP0：有则原地改写密度（长度不变），无则插入 18 字节段；不伪造 EXIF。改写与补齐都返回新数组，不修改入参。
- 三个模块均为纯函数：不建 Canvas、不读文件、不引用 Vue 或 Element Plus，符合铁律 7。测试用假编码器与合成 JPEG 段，因此能覆盖搜索逻辑与字节布局，但不能证明真实编码的体积收敛。

## T2 实施与数据流

- `core/targetKbSource.ts`：输入上限检查。复用 `avatarCrop.ts` 的 `avatarSourceSize()` 解析 JPEG SOF 与 PNG IHDR，不重写段解析；先查 20 MiB 文件体积（零成本），再查 40 MP 像素数。WebP/AVIF 解析不出尺寸时**不拒绝**，退回解码后 `checkDecodedPixels()` 补检——这一步已付出解码内存，属降级路径。另含 `fitWithinLongEdge()` 等比缩放：放这里是为了能在 Node 测试，Worker 不自带几何逻辑。
- `core/targetKbProtocol.ts`：请求带递增 `id`，`encode` 携带字节、目标区间、`allowShrink`、`dpi`；`cancel` 只带 id。`isCurrentReply(replyId, activeId)` 判断回调归属，`activeId = 0` 表示"没有有效任务"，此时任何回复都丢弃。`parseRequest()` 逐字段校验（结构化克隆不带类型信息），目标区间直接复用内核 `createTargetRange()`，不另立一套上下限。
- `workers/targetkb.worker.ts`：`inspectSource` → `createImageBitmap` → 内核二分（每次 probe 一次 `OffscreenCanvas.convertToBlob`）→ 写 DPI → COM 补齐。quality 完全由内核给出，Worker 不自行调整。
- 顺序约束：**先写 DPI 再补齐**。原图没有 JFIF APP0 时 `rewriteJfifDpi()` 会新增 18 字节，颠倒顺序会让补齐后的最终体积超出目标。
- 内存与正确性：只保留"满足上限"的编码结果（最终采用的必在其中），最多 12 份；透明图先铺白底，避免 PNG 转 JPEG 得到黑底。
- 取消与过期隔离：与妙替同一思路但下沉一层。妙替把 `revision + terminate` 放在视图层，妙压 T2 没有页面，所以 id 校验放在协议与 Worker——新请求到达即改写 `activeId`，正在跑的任务在每个 probe 前比对，发现被作废就静默退出；`cancel` 只清 `activeId`，不终止线程。妙替的协议与 worker 未改动。

## T3 页面实施

- `views/TargetKbView.vue`：只保留页头（返回首页、TARGETKB 标签、标题、副标题），状态与样式都在面板里，避免视图层同时管两件事。
- `components/TargetKbPanel.vue`：左栏选图与参数，右栏结果与下载。参数为目标上限、可选下限、是否允许缩尺寸、可选 DPI；结果给出体积变化百分比、输出尺寸与降档档数、采用质量、编码次数与耗时、补齐情况、DPI。
- 选图阶段先做轻量拦截：`inspectSourceSize(file.size)` 只比体积，`inspectSource(前 256 KiB)` 只读文件头拿像素，所以 21 MB 的文件不必进 Worker 就能给出原因。为此把体积判断抽成 `inspectSourceSize()`，让 Worker 与页面共用同一句提示，不各写一份。
- 协议新增 `progress` 回复：Worker 每完成一次试探就回报已试次数、当前质量与字节。25 MP 图不会只剩一个转圈；`progress` 与 `result` 互斥，页面收到 `progress` 不结束任务。
- 回调归属只用 id：换图、改参数、取消都把 `activeId` 归零，迟到消息直接丢弃，没有引入 revision。取消走 `cancel` 消息复用同一个 Worker，只有组件卸载才 `terminate`。
- 参数一改，上一次的结果与下载入口立刻失效（处理中改参数按取消处理并说明原因），避免用户下载到与当前设置不符的文件；实测把目标从 500KB 改成 300KB 后结果区回到空状态。
- 拖放用 Drag and Drop API（`dragover`/`drop`）而不是 Pointer Events：Pointer Events 不携带 `File`，文件拖放只有 DnD 能拿到；点击入口仍是包在 `<label>` 里的原生 file input，键盘可聚焦。
- `config/toolRegistry.ts`：`target-kb` 由 `planned` 改为 `available`；`plannedFeatures` 同时改成已交付的三项——原文案里的"常用规格"没有实现，不能留在首页搜索索引里。

## T4 批量与 ZIP

- `core/targetKbBatch.ts`：批量上限（20 张 / 合计 60 MB）、`validateBatch`、`summarizeBatch`、`sanitizeName`、`outputFileName`、`zipEntryName`。全是纯函数，6 项专项测试覆盖边界、汇总口径与命名去重。
- `components/TargetKbBatchResult.vue`：只读展示逐张状态、汇总、失败清单与下载按钮；调度、打包、取消都在面板里，子组件不持有 Blob 地址。
- `TargetKbPanel.vue`：选图改多选，1 张仍走 T3 的详细结果视图，多张走批量列表。`sendEncode()` 返回 Promise，单图与批量共用同一条 Worker 路径。
- **串行处理**：一次只解码一张。并行会让 25 MP 级图片同时占用多份画布内存，40 MP 上限就失去意义。
- **ZIP 用 `level: 0`（store）**：JPEG 已经压缩过，deflate 几乎不再变小，用 store 换更短的等待；实测 3 项 ZIP 659,433 B，仅比三项之和多 416 B 的头部开销。
- **只打包成功项**：失败项单独列在"以下 N 张未包含在 ZIP 中"，不把半成品混进包，也不静默丢弃。
- **合计只算成功项**：把失败文件的体积算进"压缩前"会让压缩率看起来虚高，属于误导；`summarizeBatch` 为此单列 `doneInputBytes`。
- ZIP 内命名 `01-原名-297KB.jpg`：序号同时解决同名覆盖与解压顺序；文件名先清掉路径分隔符与 Windows 非法字符。
- `utils/byteSize.ts`：单图与批量共用体积格式化，避免两处各写一份后口径不一致（纯函数，符合铁律 5）。
- 取消批量不保留半成品：已完成的也回到"等待"，提示"已取消本次批量，未生成结果。"

## 试用反馈修复（T4 后续）

用户在本地试用后报了三个问题，前两个是缺陷，第三个是咨询。

**1. 压缩后"待压缩的图片"缩略图变成破图（缺陷，已修）**

- 根因：`run()` 调 `invalidate()`，而 `invalidate()` 复用了 `clearUrls()`，后者把 `sourceUrl` 一并 `revokeObjectURL` 并置空；`<img :src>` 因此变空字符串，浏览器按加载失败处理。原图字节从未改动，只是缩略图的临时地址被提前回收。
- 同一根因还有第二个触发点：改目标体积、改 DPI、拨开关都会走 `invalidate()`，缩略图同样会坏。
- 修法：把清理拆成"输出侧"与"输入侧"。`clearOutputUrls()` 只撤 `resultUrl` / `zipUrl`，供 `invalidate()` 使用；`releaseEntries()` 负责撤销缩略图地址，只在换图、移除与卸载时调用。
- 经验：对象地址要按"归属"分组释放，不能用一个 `clearUrls()` 通吃；否则"作废结果"会误伤"仍然有效的输入"。

**2. 待选区没有删除交互（缺失，已补）**

- 原来单张只有一个 `<figure>`，多张只有一行"已选 N 张"，`picked` 只能被下一次选图整体覆盖。
- 改为 `PickedEntry`（`id` + `file` + `url` + 宽高 + 状态）单一列表：多张渲染带缩略图的列表，每行一个移除按钮，顶部加"清空"；单张保留大预览，在说明行加"移除"。
- **同时修掉一个隐患**：原来 `picked` / `rows` 两个平行数组靠下标对应，`outputs` 也以下标为键。删掉中间一项会让后面全部错位，ZIP 里会串图。现在 `outputs` 以 `entry.id` 为键，删除不需要重排任何东西。
- 删除会作废旧结果（ZIP 少一项、合计体积变了），避免用户下载到与当前列表不符的文件。
- 移除后只剩 1 张时自动切回单图大预览；删空回到初始态，"开始压缩"按钮恢复禁用。

**3. 上传下载是否有开销（咨询，无代码改动）**

- 全链路无 `fetch` / `axios` / `FormData` / `/api/`：`File → arrayBuffer → postMessage(transfer) → Worker 内 OffscreenCanvas → transfer 回 → createObjectURL → <a download>`。图片字节不出本机，网络流量为 0。
- 真实开销在本地：读文件进内存（20 MB 图常驻 20 MB）、解码后画布（40 MP × 4 字节 ≈ 160 MB）、以及 N 次编码的 CPU。批量另有"全部成功输出"常驻内存。

**顺手纠正一处文案**：批量结果面板原来只凭 `summary.pending > 0` 判断，选完 3 张还没点开始就显示"正在处理第 1 / 3 张"并带进度条。现增加 `running` 属性区分"等着开始"与"正在跑"，未开始时显示"待处理 N 张，点「开始压缩」开始"。

## 追加拖入（第二轮反馈）

用户试用后指出：先拖一张再拖其余几张，第二次会**替换**第一次的结果，希望改成追加到列表末尾。

- `acceptFiles()` 从"清空重建"改为**追加**：`invalidate()` 与 `releaseEntries()` 不再在入口处无条件调用。
- 新增纯函数 `mergePicked(existing, incoming)`（`core/targetKbBatch.ts`）：挡非图片、挡重复，返回 `{ added, duplicates, notImages }`。去重键是**名字 + 体积 + 修改时间**——只看名字会把"同名不同图"误判成重复，只看体积同理。
- 上限校验改成对"已有 + 新增"整体校验，超限则整批不加；**校验失败不清空已有列表**（旧代码在入口就 `invalidate()` + `releaseEntries()`，一次失败的拖入会把已选的图全清掉）。
- 上限文案从"请分批处理"改为"请减少选择或先移除部分图片"：追加语义下前者会让人以为要重开一批。
- 删到只剩一张时补解析文件头，避免大预览一直显示"尺寸待解码后确认"（批量加入的项原本没有解析过）。
- 拖放区副标题补一句"再次拖入会追加到列表末尾"，把行为写在用户看得到的地方。

## 结果出口与失败提示（第三轮反馈）

用户试用后问了三件事：不下载会不会留下无用文件、没有可视化的取消/收场入口、以及让我自查还有哪些妨碍体验的地方。

**1. 不下载不会留下文件（结论：无残留，但确实占内存）**

- 全程不写磁盘、不用 Service Worker、不用 IndexedDB；对象地址（`createObjectURL`）只是内存引用。
- 结果停留期间占用的是：每张成功输出的字节（`outputs`）＋ ZIP 的 Blob，约等于输出体积的 2 倍。这是"还能下载"的必要成本。
- 会在这些时机释放：换图/追加、改任意参数、移除某项、清空、离开页面（`onBeforeUnmount`）。因此**不存在跨操作的泄漏**，只是没有"我现在不想下载了"的出口——见第 2 条。

**2. 补上"放弃结果"（缺陷，已修）**

- 单图结果区与批量结果区各加一个次要按钮"放弃结果"，位置在下载按钮右侧。
- 行为：释放输出字节与 ZIP 地址、把逐张状态复位为"等待"，**保留已选图片与参数**，提示"已放弃结果，可调整设置后重新压缩。"用户可以只改目标体积再跑一次，不必重新选图。
- 不做二次确认：该动作可重跑恢复，不属于不可逆操作（对照 `ux-guidelines.csv` 的 Confirmation Dialogs 条目，仅删除/不可逆才需确认）。

**3. 失败时给出"最低可达体积"（缺陷，已修）**

- 原来失败只说"请放宽目标或先缩小图片"，用户不知道目标该填多少。截图里的场景正是两张图都失败、却没有任何数字可参考。
- 现在 Worker 在失败分支取所有试探里的最小字节数（即最低质量 / 最小尺寸那次的真实结果），拼进提示：
  `已降到最低质量并缩到最小尺寸，最低约 20.3 KB，仍超过目标 5.0 KB；请把目标调到 20.3 KB 以上，或先缩小图片。`
- 关闭"允许缩小尺寸"时走另一条文案（未缩小尺寸），不谎称缩过图。

**4. 顺手补一句透明说明（既有行为，未披露）**
