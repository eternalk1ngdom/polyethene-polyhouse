## T1 实施与数据流

- `core/targetKbCompress.ts` 是不可变状态机：`startSearch` 先以质量 1.0 试一次，`advanceSearch` 依据实测字节数二分并返回下一次试探、成功或失败。只以"不超过上限"为约束求最大质量，低于下限交给 COM 段补齐——区间搜索在"最高质量仍小于下限"时会无解，补齐才是正确出口。
- 尺寸降档按 0.85 连乘、最多 6 档、最短边 64px；无法再缩时返回 `failed`，**不返回超限文件**，也不静默交付一个"差不多"的结果。
- `core/jpegComInjector.ts` 只解析 SOS 之前的段，遇 SOS/EOI 停止，避免把熵编码数据误判为标记；补齐段插在头部元数据（APPn 与 COM）之后，保证 JFIF 仍是第一个段。差额 1～4 字节无法精确补齐，返回未满足而不是写出超限文件。
- DPI 只写 JFIF APP0：有则原地改写密度（长度不变），无则插入 18 字节段；不伪造 EXIF。改写与补齐都返回新数组，不修改入参。
- 三个模块均为纯函数：不建 Canvas、不读文件、不引用 Vue 或 Element Plus，符合铁律 7。测试用假编码器与合成 JPEG 段，因此能覆盖搜索逻辑与字节布局，但不能证明真实编码的体积收敛。

## T2 实施与数据流

- `core/targetKbSource.ts`：输入上限检查。复用 `avatarCrop.ts` 的 `avatarSourceSize()` 解析 JPEG SOF 与 PNG IHDR，不重写段解析；先查 20 MiB 文件体积（零成本），再查 40 MP 像素数。WebP/AVIF 解析不出尺寸时**不拒绝**，退回解码后 `checkDecodedPixels()` 补检——这一步已付出解码内存，属降级路径。另含 `fitWithinLongEdge()` 等比缩放：放这里是为了能在 Node 测试，Worker 不自带几何逻辑。
- `core/targetKbProtocol.ts`：请求带递增 `id`，`encode` 携带字节、目标区间、`allowShrink`、`dpi`；`cancel` 只带 id。`isCurrentReply(replyId, activeId)` 判断回调归属，`activeId = 0` 表示"没有有效任务"，此时任何回复都丢弃。`parseRequest()` 逐字段校验（结构化克隆不带类型信息），目标区间直接复用内核 `createTargetRange()`，不另立一套上下限。
- `workers/targetkb.worker.ts`：`inspectSource` → `createImageBitmap` → 内核二分（每次 probe 一次 `OffscreenCanvas.convertToBlob`）→ 写 DPI → COM 补齐。quality 完全由内核给出，Worker 不自行调整。
- 顺序约束：**先写 DPI 再补齐**。原图没有 JFIF APP0 时 `rewriteJfifDpi()` 会新增 18 字节，颠倒顺序会让补齐后的最终体积超出目标。
- 内存与正确性：只保留"满足上限"的编码结果（最终采用的必在其中），最多 12 份；透明图先铺白底，避免 PNG 转 JPEG 得到黑底。
- 取消与过期隔离：与妙替同一思路但下沉一层。妙替把 `revision + terminate` 放在视图层，妙压 T2 没有页面，所以 id 校验放在协议与 Worker——新请求到达即改写 `activeId`，正在跑的任务在每个 probe 前比对，发现被作废就静默退出；`cancel` 只清 `activeId`，不终止线程。妙替的协议与 worker 未改动。

## T3 页面实施

- `views/TargetKbView.vue`：只保留页头（返回首页、TARGETKB 标签、标题、副标题），状态与样式都在面板里，避免视图层同时管两件事。
- `components/TargetKbPanel.vue`：左栏选图与参数，右栏结果与下载。参数为目标上限、可选下限、是否允许缩尺寸、可选 DPI；结果给出体积变化百分比、输出尺寸与降档档数、采用质量、编码次数与耗时、补齐情况、DPI。
- 选图阶段先做轻量拦截：`inspectSourceSize(file.size)` 只比体积，`inspectSource(前 256 KiB)` 只读文件头拿像素，所以 21 MB 的文件不必进 Worker 就能给出原因。为此把体积判断抽成 `inspectSourceSize()`，让 Worker 与页面共用同一句提示，不各写一份。
- 协议新增 `progress` 回复：Worker 每完成一次试探就回报已试次数、当前质量与字节。25 MP 图不会只剩一个转圈；`progress` 与 `result` 互斥，页面收到 `progress` 不结束任务。
- 回调归属只用 id：换图、改参数、取消都把 `activeId` 归零，迟到消息直接丢弃，没有引入 revision。取消走 `cancel` 消息复用同一个 Worker，只有组件卸载才 `terminate`。
- 参数一改，上一次的结果与下载入口立刻失效（处理中改参数按取消处理并说明原因），避免用户下载到与当前设置不符的文件；实测把目标从 500KB 改成 300KB 后结果区回到空状态。
- 拖放用 Drag and Drop API（`dragover`/`drop`）而不是 Pointer Events：Pointer Events 不携带 `File`，文件拖放只有 DnD 能拿到；点击入口仍是包在 `<label>` 里的原生 file input，键盘可聚焦。
- `config/toolRegistry.ts`：`target-kb` 由 `planned` 改为 `available`；`plannedFeatures` 同时改成已交付的三项——原文案里的"常用规格"没有实现，不能留在首页搜索索引里。

## T4 批量与 ZIP

- `core/targetKbBatch.ts`：批量上限（20 张 / 合计 60 MB）、`validateBatch`、`summarizeBatch`、`sanitizeName`、`outputFileName`、`zipEntryName`。全是纯函数，6 项专项测试覆盖边界、汇总口径与命名去重。
- `components/TargetKbBatchResult.vue`：只读展示逐张状态、汇总、失败清单与下载按钮；调度、打包、取消都在面板里，子组件不持有 Blob 地址。
- `TargetKbPanel.vue`：选图改多选，1 张仍走 T3 的详细结果视图，多张走批量列表。`sendEncode()` 返回 Promise，单图与批量共用同一条 Worker 路径。
- **串行处理**：一次只解码一张。并行会让 25 MP 级图片同时占用多份画布内存，40 MP 上限就失去意义。
- **ZIP 用 `level: 0`（store）**：JPEG 已经压缩过，deflate 几乎不再变小，用 store 换更短的等待；实测 3 项 ZIP 659,433 B，仅比三项之和多 416 B 的头部开销。
- **只打包成功项**：失败项单独列在"以下 N 张未包含在 ZIP 中"，不把半成品混进包，也不静默丢弃。
- **合计只算成功项**：把失败文件的体积算进"压缩前"会让压缩率看起来虚高，属于误导；`summarizeBatch` 为此单列 `doneInputBytes`。
- ZIP 内命名 `01-原名-297KB.jpg`：序号同时解决同名覆盖与解压顺序；文件名先清掉路径分隔符与 Windows 非法字符。
- `utils/byteSize.ts`：单图与批量共用体积格式化，避免两处各写一份后口径不一致（纯函数，符合铁律 5）。
- 取消批量不保留半成品：已完成的也回到"等待"，提示"已取消本次批量，未生成结果。"

## 试用反馈修复（T4 后续）

用户在本地试用后报了三个问题，前两个是缺陷，第三个是咨询。

**1. 压缩后"待压缩的图片"缩略图变成破图（缺陷，已修）**

- 根因：`run()` 调 `invalidate()`，而 `invalidate()` 复用了 `clearUrls()`，后者把 `sourceUrl` 一并 `revokeObjectURL` 并置空；`<img :src>` 因此变空字符串，浏览器按加载失败处理。原图字节从未改动，只是缩略图的临时地址被提前回收。
- 同一根因还有第二个触发点：改目标体积、改 DPI、拨开关都会走 `invalidate()`，缩略图同样会坏。
- 修法：把清理拆成"输出侧"与"输入侧"。`clearOutputUrls()` 只撤 `resultUrl` / `zipUrl`，供 `invalidate()` 使用；`releaseEntries()` 负责撤销缩略图地址，只在换图、移除与卸载时调用。
- 经验：对象地址要按"归属"分组释放，不能用一个 `clearUrls()` 通吃；否则"作废结果"会误伤"仍然有效的输入"。

**2. 待选区没有删除交互（缺失，已补）**

- 原来单张只有一个 `<figure>`，多张只有一行"已选 N 张"，`picked` 只能被下一次选图整体覆盖。
- 改为 `PickedEntry`（`id` + `file` + `url` + 宽高 + 状态）单一列表：多张渲染带缩略图的列表，每行一个移除按钮，顶部加"清空"；单张保留大预览，在说明行加"移除"。
- **同时修掉一个隐患**：原来 `picked` / `rows` 两个平行数组靠下标对应，`outputs` 也以下标为键。删掉中间一项会让后面全部错位，ZIP 里会串图。现在 `outputs` 以 `entry.id` 为键，删除不需要重排任何东西。
- 删除会作废旧结果（ZIP 少一项、合计体积变了），避免用户下载到与当前列表不符的文件。
- 移除后只剩 1 张时自动切回单图大预览；删空回到初始态，"开始压缩"按钮恢复禁用。

**3. 上传下载是否有开销（咨询，无代码改动）**

- 全链路无 `fetch` / `axios` / `FormData` / `/api/`：`File → arrayBuffer → postMessage(transfer) → Worker 内 OffscreenCanvas → transfer 回 → createObjectURL → <a download>`。图片字节不出本机，网络流量为 0。
- 真实开销在本地：读文件进内存（20 MB 图常驻 20 MB）、解码后画布（40 MP × 4 字节 ≈ 160 MB）、以及 N 次编码的 CPU。批量另有"全部成功输出"常驻内存。

**顺手纠正一处文案**：批量结果面板原来只凭 `summary.pending > 0` 判断，选完 3 张还没点开始就显示"正在处理第 1 / 3 张"并带进度条。现增加 `running` 属性区分"等着开始"与"正在跑"，未开始时显示"待处理 N 张，点「开始压缩」开始"。

## 追加拖入（第二轮反馈）

用户试用后指出：先拖一张再拖其余几张，第二次会**替换**第一次的结果，希望改成追加到列表末尾。

- `acceptFiles()` 从"清空重建"改为**追加**：`invalidate()` 与 `releaseEntries()` 不再在入口处无条件调用。
- 新增纯函数 `mergePicked(existing, incoming)`（`core/targetKbBatch.ts`）：挡非图片、挡重复，返回 `{ added, duplicates, notImages }`。去重键是**名字 + 体积 + 修改时间**——只看名字会把"同名不同图"误判成重复，只看体积同理。
- 上限校验改成对"已有 + 新增"整体校验，超限则整批不加；**校验失败不清空已有列表**（旧代码在入口就 `invalidate()` + `releaseEntries()`，一次失败的拖入会把已选的图全清掉）。
- 上限文案从"请分批处理"改为"请减少选择或先移除部分图片"：追加语义下前者会让人以为要重开一批。
- 删到只剩一张时补解析文件头，避免大预览一直显示"尺寸待解码后确认"（批量加入的项原本没有解析过）。

## 结果出口与失败提示（第三轮反馈）

用户试用后问了三件事：不下载会不会留下无用文件、没有可视化的取消/收场入口、以及让我自查还有哪些妨碍体验的地方。

**1. 不下载不会留下文件（结论：无残留，但确实占内存）**

- 全程不写磁盘、不用 Service Worker、不用 IndexedDB；对象地址（`createObjectURL`）只是内存引用。
- 结果停留期间占用的是：每张成功输出的字节（`outputs`）＋ ZIP 的 Blob，约等于输出体积的 2 倍。这是"还能下载"的必要成本。
- 会在这些时机释放：换图/追加、改任意参数、移除某项、清空、离开页面（`onBeforeUnmount`）。因此**不存在跨操作的泄漏**，只是没有"我现在不想下载了"的出口——见第 2 条。

**2. 补上"放弃结果"（缺陷，已修）**

- 单图结果区与批量结果区各加一个次要按钮"放弃结果"，位置在下载按钮右侧。
- 行为：释放输出字节与 ZIP 地址、把逐张状态复位为"等待"，**保留已选图片与参数**，提示"已放弃结果，可调整设置后重新压缩。"用户可以只改目标体积再跑一次，不必重新选图。
- 不做二次确认：该动作可重跑恢复，不属于不可逆操作（对照 `ux-guidelines.csv` 的 Confirmation Dialogs 条目，仅删除/不可逆才需确认）。

**3. 失败时给出"最低可达体积"（缺陷，已修）**

- 原来失败只说"请放宽目标或先缩小图片"，用户不知道目标该填多少。截图里的场景正是两张图都失败、却没有任何数字可参考。
- 现在 Worker 在失败分支取所有试探里的最小字节数（即最低质量 / 最小尺寸那次的真实结果），拼进提示：
  `已降到最低质量并缩到最小尺寸，最低约 20.3 KB，仍超过目标 5.0 KB；请把目标调到 20.3 KB 以上，或先缩小图片。`
- 关闭"允许缩小尺寸"时走另一条文案（未缩小尺寸），不谎称缩过图。

## DPI 写入顺序修正

**问题**：原实现在搜索**结束后**才写 DPI。搜索期间判定"是否 ≤ 上限"用的是编码器返回的长度；若编码器不带 JFIF APP0，`rewriteJfifDpi()` 会插入 18 字节，最终文件就会比目标多 18 字节。Chrome 的 `convertToBlob` 恒写 APP0，所以本地从未触发——这是被浏览器行为掩盖的潜在缺陷。

**修法**：把写 DPI 前移到每次试探之后、判定之前，并抽出 `prepareDelivery(encoded, dpi)`（`core/jpegComInjector.ts`）作为唯一入口：

```ts
const measured = prepareDelivery(encoded.bytes, request.dpi)
// 之后 probes / 候选 / advanceSearch / 进度一律用 measured.byteLength
```

- 候选里存的就是交付字节，结尾不再二次改写（否则会重复插入 APP0）。
- 顺带修正一处口径不一致：`needsPadding` 的 `padToBytes` 现在基于交付长度计算，与最终文件一致。
- 代价：每次试探多一次数组拷贝（约 100 KB 级），相对一次编码可忽略。

**为什么用函数而不是就地改**：这条顺序约束原先只写在注释里，容易被后续改动破坏；`prepareDelivery` 给它一个名字，测试可以直接锁住"交付长度才是判定依据"。

**回归验证（Chrome，真实 JPEG）**：

| 场景 | 结果 |
| --- | --- |
| 3840×2400、目标 500KB、**不写 DPI** | 492.1 KB，q=0.88，11 次 |
| 同一张、**写 DPI 300** | 492.1 KB，q=0.88，11 次——与不写 DPI **完全一致**，证明 Chrome 下改写不改变长度 |
| 下载文件核对 | 503,959 字节，≤ 500KB；JFIF APP0 `unit=1, x=300, y=300`，与 T2 验收记录的字节数分毫不差 |
| 280×175、目标 60KB + 下限 60KB + DPI 300 | 23.1 KB → **61,440 字节整**，补 12.5 KB 注释段；COM 补齐路径未受影响 |

**未验**：没有"不写 APP0 的编码器"可供实测（Chrome/Edge 都写 APP0，Firefox/Safari 未接入自动化）。该路径由单元测试与代码构造保证，不是浏览器实测结论。

自动化：`npm test` **187 通过**（新增 1 项 `prepareDelivery` 顺序约束）；`lint:check`、`build` 退出 0。

## 内核搜索次数优化

**问题**：25.6 MP 图压到 120 KiB 要编码三十多次、等五到八秒。原策略在每一档都从 q=1.0 起做纯二分，区间要收到 0.001 才算收敛——**每档约 12 次**。而"这一档靠质量根本压不下来"的结论，本可以用两次编码就得到：顶格一次、探底一次。

**改法**（`core/targetKbCompress.ts`）：

1. **探底优先**：某次试探超限、且字节数达到上限的 `FLOOR_PROBE_RATIO`（8）倍时，下一次不再取区间中点，而是直接编码 `MIN_QUALITY`。
   - 探底仍超限 → `high` 落到 0.1、与 `low` 重合，区间自然塌缩，下一步直接降档，整档只花 2 次编码；
   - 探底能装下 → 质量区间两端都有了实测值，后续二分照旧，结果与原来一致。
   - 阈值取 8 有依据：同一张照片 q=1.0 与 q=0.1 的字节数通常相差 8～12 倍，正好是"最低质量也可能装不下"的界线；低于它说明区间里必有解，逐格二分更快，不必多花这一次。
2. **收敛阈值放宽到 0.005**（原 0.001）。从 0.9 的区间收到 0.001 要十次二分，收到 0.005 只要八次；而质量差 0.005 在同一张照片上通常不到 1% 体积，肉眼看不出来。三次实测中输出字节**完全一致**，证明这一步没有牺牲结果。

状态新增一个 `floorProbed` 布尔位，只用于"同一档位不重复探底"；降档时复位。

**A/B 实测**（Chrome 156.0.8078.79 headless，同一张 6400×4000、源 9,037,240 字节的合成照片，同一个 Canvas 编码器，新旧内核各跑一遍）：

| 目标 | 旧内核 | 新内核 | 输出字节 |
| --- | --- | --- | --- |
| 120 KiB | 44 次 / 12.75 s / q=0.1448 / 降档 3 | **16 次 / 6.08 s** / q=0.1422 / 降档 3 | 均 118,462 B，尺寸均 4624×2890 |
| 500 KiB | 11 次 / 3.16 s / q=0.2143 / 降档 0 | **10 次 / 2.90 s** / q=0.2125 / 降档 0 | 均 459,143 B |
| 3 MiB | 11 次 / 3.96 s / q=0.6845 / 降档 0 | **9 次 / 3.19 s** / q=0.6836 / 降档 0 | 均 2,990,776 B |

- 前六次试探的顺序差异（120 KiB）：旧 `1.0 → 0.55 → 0.325 → 0.2125 → 0.1563 → 0.1281`，新 `1.0 → 0.1 → 1.0@5440 → 0.1@5440 → 1.0@4624 → 0.1@4624`——旧内核在前两档各花了 12 次才承认"压不下来"，新内核每档 2 次就降档。

| 目标 | 编码次数 | 结果 | DPI |
| --- | --- | --- | --- |
| 500 KiB | 9（进度回调 9 条） | 504,367 B，q=0.8418，未降档 | 300 写入成功 |

## 真实输入补验与百万像素口径修正

T1～T4 有几条路径只验过逻辑、没拿真样本跑过。本轮用真实浏览器与真实 Worker 补齐三条，并修掉其中暴露的一个文案错误。

**用例与结果**（Chrome 156.0.8078.79 headless，真 Worker 协议）：

| 用例 | 输入 | 结果 |
| --- | --- | --- |
| 带透明通道的 PNG | 800×600，左半不透明红、右半全透明，11,853 字节 | 输出 JPEG 7,022 字节、q=1.0；**回解码采样：左半 `[254,0,0]`、右半 `[255,255,255]`**——透明区域确实是白底而不是黑底 |
| 真实 WebP | 1200×800，`convertToBlob({type:'image/webp'})` 产出，RIFF/WEBP 头校验通过，70,176 字节 | 成功转 JPEG 147,923 字节，尺寸 1200×800 未变，q=0.94375，9 次编码 |
| 真实的 43.2 MP 图 | 8000×5400，294,782 字节 | 16 ms 内 `pixels-too-large`，**进度回调 0 条**（解码前就拦下），未产生任何编码 |

**修正：百万像素按 10⁶ 算**。上表第三条原本提示"图片为 8000×5400（41.2MP）"——而 8000×5400 = 43,200,000 像素，也就是 43.2MP，用户自己一乘就知道对不上。原因是 `toMegapixels()` 用了 `1024 * 1024` 做除数。已改为 `1000000`，现在提示"图片为 8000×5400（43.2MP），超过 40MP 上限"，并补了一条测试钉住。

**注意**：只改了**显示**。上限常量 `MAX_SOURCE_PIXELS` 仍是 `40 * 1024 * 1024`（41,943,040 像素），因为 `target-kb-source.test.mjs` 用 `assert.equal(MAX_SOURCE_PIXELS, 40 * 1024 * 1024)` 显式钉过，说明当初是有意选的二进制口径。要不要改成 40,000,000 让"40MP"字面成立，是产品边界决定，见「未完成与风险」。

## 已满足目标时原样交付（不再越压越大）

**问题**：目标上限设得比原图大时，输出反而变大。真实 WebP 70,176 字节、目标 150 KB → 输出 **147,923 字节（+111%）**；更早的小图样本 23.6 KB → 48.6 KB 同理。

**根因**：不是搜索算错，是参照物选错。搜索第一发永远是 q=1.0，判据是"≤ 目标上限即成功"，而 q=1.0 重编码出的 JPEG 恒大于已经压过的源文件（二次有损编码、WebP 本身更省），于是"上限"变成了"把预算填满"。

**修法**：进搜索之前先判一次——源文件本身是否已落在目标区间内（`core/targetKbCompress.ts` 的 `planDelivery()`）：

| 源文件状态 | 处理 |
| --- | --- |
| 已在区间内、未要求写 DPI | **原样返回，完全不编码**：字节 0% 变化、零画质损失、耗时接近 0 |
| 已在区间内、要求写 DPI、源是 JPEG | 只改 JFIF APP0，不动像素；若因此多出 18 字节导致超限，退回编码 |
| 已在区间内、要求写 DPI、源不是 JPEG | 只有转成 JPEG 才带得上 APP0，走编码 |
| 低于下限（要求增重） | 走编码 + COM 补齐 |
| 超过上限 | 走编码 |

连带改动：协议新增 `passthrough` 与 `mime`，`quality` 改为可空；页面显示"原图已在目标体积内，无需压缩"并隐藏质量/编码次数；下载与 ZIP 内后缀跟随实际输出类型（`mimeExtension()`）；批量行显示"无需压缩"。

**验收**（Chrome 156.0.8078.79 headless，真 Worker 协议）：

| 用例 | 输入 | 结果 |
| --- | --- | --- |
| 真实 WebP 1200×800 + 目标 150 KB | 70,176 B | **原样返回 70,176 B**（逐字节比对相同），`image/webp`，0 次编码，10 ms |
| 真实 JPEG 1200×800 + 目标 200 KB | 129,362 B | 原样返回 129,362 B，0 ms |
| 同上 + DPI 300 | 129,362 B | 长度不变（原地改写 APP0），回读 `dpi=300` |
| 带透明 PNG 800×600 + 目标 200 KB | 11,853 B | 原样返回 `image/png`，**透明通道保留** |
| 同一张 PNG + 目标 3 KB（强制压缩） | 11,853 B | 压缩：3,057 B JPEG，q=0.49，降档 2 次（578×434），透明区采样 `[255,255,255]` |

**代价（已知且已确认）**：输出不再恒定是 JPEG——源文件已满足目标时保持原格式。因此"PNG 透明区域变白底"只在真正发生压缩时成立，页面文案已同步改成"需要压缩时才转成 JPEG"。

**顺带修正**：`MAX_SOURCE_PIXELS` 从 `40 * 1024 * 1024`（41,943,040 像素）改为 `40 * 1000000`，让"40 MP 上限"字面成立。影响是 40.0M～41.9M 像素这一段由放行改为拒绝，测试里的边界样本同步换成 8000×5000（正好 40,000,000）。

## 浏览器能力检测（收尾自查发现）

**问题**：整个前端没有一处 `OffscreenCanvas` 存在性检查。Worker 里直接 `new OffscreenCanvas(...)` + `convertToBlob()`，而 Safari 要到 16.4 才支持 Worker 内的 `OffscreenCanvas.convertToBlob`，Firefox 更晚。这些浏览器上会走 `TargetKbPanel.vue` 的 `onerror`，显示"本地编码线程出错，请重试"——用户重试多少次都不会好，因为能力由浏览器版本决定，界面上也没有任何提示指向真正原因。

妙替那边本来就有这个习惯（`PolyReplaceView.vue` 的"当前浏览器不支持选择文件夹，可改为选择文件"），妙压缺这一层是自己漏的。

**修法**：判定与文案拆到 `core/targetKbCapability.ts`（纯函数 `describeCapabilityGap()`，接收能力对象、不引用浏览器全局，符合铁律 7 对 `core/` 的限制），探测动作留在组件里：

```ts
function detectCapability(): TargetKbCapability {
  const hasOffscreenCanvas = typeof OffscreenCanvas !== 'undefined'
  return {
    worker: typeof Worker !== 'undefined',
    createImageBitmap: typeof createImageBitmap === 'function',
    offscreenCanvas: hasOffscreenCanvas,
    // Safari 16.4 之前有构造器却没有 convertToBlob，只看构造器会误判成支持
    convertToBlob:
      hasOffscreenCanvas && typeof OffscreenCanvas.prototype.convertToBlob === 'function',
  }
}
```

四项缺任一都返回同一句提示（四项都指向"浏览器太旧"，分项提示只会让用户猜哪项重要）："当前浏览器不支持本地图片编码，请改用 Chrome、Edge，或 Safari 16.4 及以上版本。"

界面行为：页面顶部显示 error 级提示条；"开始压缩"按钮在有图时也保持禁用；**选图与拖入不禁用**——先让用户看到图，再告诉他为什么不能压，比一进页面就锁死上传区更好理解。`onerror` 文案同时补上"若反复出现，请改用 Chrome、Edge 或 Safari 16.4 及以上版本"，兜住能力检测漏判与 OOM 两类原因。

**验收**（Chrome 156.0.8078.79 headless，用 `Page.addScriptToEvaluateOnNewDocument` 在应用脚本执行前 `delete OffscreenCanvas.prototype.convertToBlob`，模拟 Safari 16.3 的真实形态）：

| --- | --- | --- | --- | --- |
| A 正常 Chrome | 有构造器、有 `convertToBlob` | 无 | 1 张（3840×2400，1.53 MB） | 可用 |
| B 模拟 Safari 16.3 | 有构造器、`convertToBlob` 为 `undefined` | 1 条，文案完整 | 1 张（同一文件） | **禁用** |

两行都注入了同一张图，所以 B 的禁用确定来自能力判定，而不是"列表为空"。窄屏 390×844：提示条 `left=41 / right=349 / width=308`，`scrollWidth == innerWidth`，无横向溢出；桌面 1280×900 截图确认提示条不遮挡标题与上传区。截图见 `%TEMP%/cap-A-supported.png`、`cap-B-unsupported.png`、`cap-B-narrow.png`。
