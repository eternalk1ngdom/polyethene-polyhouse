## 用户目标与本轮范围

- 下一阶段先完成受控内测所需改造，再安排上线，邀请少量指定朋友使用；不继续扩展妙压、留言、社区、云模板或 AI。保持方案二视觉和既有依赖版本。
- 取消公共自助注册，由屋主自行创建并发放测试账号。所有会被他人看到的用户内容先经屋主确认；头像必须审核后发布，不能上传即生效。昵称等现有展示字段同样纳入检查，不为此提前开放新编辑入口。
- 候选部署结构：同机 Nginx 提供前端和 `/api` 代理，后端连接本机 MySQL/Redis；IP + 自定义端口是访问形式，不等于备案豁免或访问控制。正式开放方式尚未确定。
- 本轮仅核对现状、确定顺序并记录计划，不声称已经关闭注册、实现审核、获得平台许可或上线。不会修改朋友服务器、防火墙或真实屋主资料。

## 已核对的实现基线

- `AuthController` 的 `POST /api/auth/register` 使用 `@SkipBearerAuth`，当前是公共入口；前端仍有注册表单。只隐藏前端入口不能阻止直接 HTTP 开户。
- `RegisterDTO` 已约束账号、昵称及 BCrypt 的密码长度；现有服务使用密码哈希和唯一性保障，可供受控开户复用，不应改成手写 SQL 填明文密码。
- `AvatarService.upload` 校验/重新编码图片，锁定用户行、更新当前头像和每日次数；事务结束后处理新旧文件补偿。当前没有待审核状态。
- `AvatarWebConfig` 将受控随机文件名映射为公开资源，并允许一天 HTTP 缓存；待审图片不能继续写入这一公开目录。随机地址不构成权限控制。
- 本地图片与数据库分开持久化，现状见[头像说明](../operations/avatar-storage.md)。留言未实现；其他资料编辑与 OSS 也未实现。既有唯一 OWNER、登录/成长、软注销和妙替能力保持。

## 按顺序实施与验收

### 1. 关闭公共注册，补齐屋主创建测试账号

- 服务端关闭公共注册路径，直接发送注册请求也不能新增账号；前端移除注册切换、入口和误导文案，保留已有账号登录。
- 首版优先采用受控运维命令创建测试账号，与现有屋主初始化命令一样不作为网页静态资源发布；复用独立业务服务、参数校验、密码哈希和唯一索引。具体命令参数在实现时确定。
- 运维命令需要服务器或本机运维权限，不是普通用户可调用的注册替代接口；操作前精确核对目标环境和操作者权限，不在命令历史、日志、Git 或输出中记录密码。发放凭据使用私密渠道。
- 新账号默认 USER；内测身份与 INSIDER 的付费/高开销权限分开，不能仅因是朋友就自动提权，也不能创建第二个 OWNER。
- 创建时由屋主确定账号及昵称；不新增普通用户自由修改昵称、简介等可见字段的能力。现有账号与头像先只读列出核对项，不擅自删除或修改真实屋主。
- 验收：公共接口拒绝且用户数不变；命令成功/重复账号/非法参数/失败回滚；既有账号登录、奖励和退出正常，权限及会话不被意外改写。

### 2. 头像改为私有待审与审核发布

- 将提交、审核和发布拆为清楚的职责；新增独立审核服务及必要持久化记录，避免把状态机全部塞进认证服务。沿用现有图片校验、存储抽象与事务补偿思路。
- 流程：用户提交 → 私有待审 → OWNER 通过或驳回；通过后才更新公开头像。审核期间其他页面继续显示原已批准头像或默认头像。
- 待审文件存于独立私有目录，无公开静态映射；受鉴权的查看入口仅允许提交者本人和 OWNER，校验资源归属，不因知道文件编号就允许读取。前端需按鉴权方式读取图片，不能假设 `<img>` 自动携带 Bearer 头。
- 通过后生成新的公开资源地址；驳回不改变现有公开头像；新增下架能力以恢复默认头像。旧缓存或已被下载的图片不能承诺立即从所有客户端消失。
- 记录提交版本、状态、审核人、审核时间和必要原因；一次审核只作用于对应版本。重复审核、旧版本审核与用户重新提交/注销并发不能覆盖新状态。
- 保留并明确每日提交限制、防重复与私有文件容量/保留期限；不能用反复提交或驳回无限占盘。次数含义、失效清理与具体数据迁移在本模块实现时一并说明并验证。
- 既有头像先清点，由屋主确认后保留发布或撤下；不能默认历史头像已审核，也不在本轮直接执行批量撤下。迁移、备份和恢复须覆盖数据库、私有图及公开图。
- 验收：未登录/越权查看与审核、猜测路径、私有图直链拒绝、通过/驳回/下架、重复及过期审核、注销并发、磁盘/事务失败、配额和文件清理；确认不发生先公开后审核。

### 3. 最小屋主审核入口与前端接入

- 只提供完成本次审核所需的待审列表、受控预览、通过/驳回、已发布头像下架入口；由 OWNER 访问，后端逐个接口独立校验权限，不依赖前端隐藏按钮。
- 普通用户看到自己的待审/驳回状态和必要原因，提交成功文案改为“等待审核”；公共导航、个人小窗、个人页仍只显示当前批准的头像。
- 页面继续使用现有 Element Plus、类型接口与独立业务组件；不加入通用 CMS、社交系统或全新视觉改版。

### 4. 合并验收与阶段收口

- 每个闭环按约定编译、构建、补充相关定向验证，代码、测试与日志一起本地提交；远端推送仍需明确授权。
- 最后合并验证匿名/USER/INSIDER/OWNER 权限矩阵、直接 HTTP 绕过尝试、审核并发与失败恢复，以及原登录、每日奖励、退出/软注销、妙替预览和 ZIP 下载的关键回归。
- 使用独立测试库/精确随机夹具，不在已有正式 OWNER 的开发库执行含 OWNER 夹具的全量实例测试；真实图片和账号不能作为可清理的测试数据。
- 历史验收仅作基线；本阶段尚未实施，不把上一阶段的通过数量当作新审核能力的验收结果。

### 5. 完成上述改造后再准备上线

- 先核实平台对具体内测方式的要求，再确定网络入口范围及开放期限；需要时向当地通信管理局确认适用义务。少量账号、人工审查、非盈利、IP 或非标准端口均不记为自动合规豁免。
- 普通账号登录不等于网络访问限制；若确定受限内测，另行落实入口访问控制。公网纯 HTTP 不能保护密码和 Token，上线验收前要确定可信 HTTPS 或其他加密访问链路。
- 朋友服务器信息仅来自用户截图：Ubuntu 22.04、2 核/2GB 标称内存、40GB 磁盘、3Mbps；截图当时可用内存约 965MiB、无 Swap，已有 Python 服务。实际安装前重新核对，不按截图保证当前容量，不停用朋友服务。
- 独立用户、目录、数据库账号及服务；MySQL/Redis 不暴露公网。按实测设置进程/连接/上传/日志限额，不能把 Java 堆上限当作进程总内存上限。
- 准备版本目录、发布切换、健康检查和回退；数据库迁移优先追加兼容，代码回退不自动撤销数据迁移。备份同时覆盖数据库、图片与必要私有配置，执行恢复验证。
- 单机内测先用本地持久目录，OSS 为后续可选迁移，不作为本阶段强制采购；不因准备部署升级框架版本。

- 新增 `POST /api/auth/password/change`，Body 为 `currentPassword/newPassword`，Bearer 身份；成功 `Result<Void>`。资料 VO 新增 `passwordChangeRequired`，不返回凭据版本或密码哈希。JWT 增加版本声明，历史缺失仅视为 0，且须与数据库匹配；回归发现库会丢弃显式 null，已增加已验签历史格式分支的原始字段核对并重跑通过，新 Token 不增加第二次 JSON 解析。
- 登录/成长沿用同一用户行锁做版本检查，不额外增加完整身份查询；首次凭据仅可读本人、改密和退出，HTTP 403/业务码 40301 与真正失效 401 分开。头像直接服务入口及软注销也检查首次限制；未改密暂不发每日奖励，改密后重新登录按原规则结算一次。
- 前端新增独立密码弹窗并挂到公共导航，个人中心增加入口；临时凭据自动弹出且不能直接关闭，允许退出。凭据只存本次表单；校验/关闭/卸载/换号使旧回调失效，提交去重，跨标签页或旧 401/成功不能清理新账号。请求结果未知不自动重发；成长与上传/注销入口同步受限。
- `Invoke-LocalAuth.ps1 -Action Verify -AccountSecurityOnly` 复用私有预设，仅运行随机独立 MySQL 库的安全验收，隔离签名密钥和夹具；普通验收明确关闭该开关。容量隔离测试的建库迁移清单补 005，本轮未重复容量压测。README 与[账号安全说明](../operations/account-security.md)说明接口、迁移、私有备份、恢复边界及后续步骤。
